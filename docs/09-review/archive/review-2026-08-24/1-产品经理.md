# Proxy Rebuild 字段级产品评审报告

评审范围：四份文档（README / FUNCTIONS / CLAUDE / PROJECT-STATUS）、`multi-proxy-manager/server.js`（1413 行）、4 个 HTML 页面（约 5900 行），并对 codex/hermes/cursor 三个代理的相关端点做了交叉验证。

## 一、做得好的地方

1. **安全设计成熟度高于同类内部工具**：JWT secret 持久化到 `~/.multi-proxy-jwt-secret` 且 0600 权限（server.js:16-71）；登录双 limiter（每分钟 5 次 + 15 分钟锁定，server.js:953-974）；转发白名单对 `:id` 做 UUID/数字/字母数严格校验（server.js:1069-1081）；spawn 有 cwd realpath + symlink 校验和命令白名单（server.js:460-514）。
2. **stopProxy 的 PID 白名单防误杀设计正确**：只 kill 属于本代理追踪树的 PID（server.js:598-651），避免误杀恰好占用同端口的无辜进程。
3. **崩溃恢复完整**：指数退避 + 连续 5 次进入 fault state + 状态持久化到 crash-recovery.json（server.js:533-565, 269-316）。
4. **前端 XSS 防护一致**：所有插值走 `esc()`，复制功能用 `data-*` + 事件委托（proxy-config.html:1984-2026），P0 修复记录与代码对得上。
5. **文档纪律罕见地好**：NO_PROXY 铁律、lsof 绝对路径、路由注册顺序等“踩坑记忆”沉淀进了 CLAUDE.md，这是有效的组织资产。
6. **跨页状态同步**（BroadcastChannel，dashboard.html:1379-1387）和乐观更新让启停操作手感良好。

## 二、Bug（按严重度排序）

**B1〔P0〕日志页解析格式与后端写入格式完全不匹配，四大过滤器全部失效**
- 后端 `appendLog` 写的是 JSON Lines：`{"ts":"...","level":"INFO","proxy":"...",...}`（server.js:196-218）
- 前端正则却按 `[ts] [LEVEL] [proxy] msg` 纯文本解析（logs.html:747）：`/^\[([^\]]+)\]\s+\[(\w+)\]\s+\[([^\]]+)\]\s+(.*)$/`
- JSON 行永不匹配 → 全部落入 else 分支（logs.html:756-761）：级别一律 INFO、代理一律 system、时间戳一律“当前时刻”。结果是：级别筛选、代理筛选、时间范围筛选、ERROR 排查全部不可用。这是日志页这个核心功能的静默失效。

**B2〔P0〕忘记密码指引指向不存在的文件，照做无法重置**
- login.html:755 与 copyResetCommand（1140）让用户执行 `rm ~/.multi-proxy-password`，README L243 同样写错；
- 实际密码文件是 `~/.multi-proxy-manager/password`（server.js:75）。用户被锁在门外时唯一的自助通道是断的。

**B3〔P1〕三处「delete 之后 kill」死代码，启动失败的僵尸进程永远不会被 SIGKILL**
- server.js:694-695、767-768、836-837 均为 `delete proxyProcesses[name]; if (proxyProcesses[name]) proc.kill('SIGKILL')` —— delete 后条件恒 false。端口绑定超时时残留进程只能靠 5 秒超时的 lsof 兜底，属于明显的语句顺序写反。

**B4〔P1〕切换历史整个是假的**
- renderHistory 只读硬编码 MOCK_HISTORY（proxy-config.html:1747-1762，数据是 2026-06-27 的假记录），clearHistory 只清内存数组（1775-1780）；
- 后端白名单里明明有 `/api/history`（server.js:1035-1044），前端从不调用。FUNCTIONS.md §2.4 宣称“切换历史—记录模型切换操作”，属宣传与实现的断头路。

**B5〔P1〕Codex/Hermes 的「模型切换」按钮静默无效**
- switchModel() 只打 cursor 的 `admin-api/settings` PUT（proxy-config.html:922-931）；codex/hermes 的正确端点 `/api/switch-model` 在白名单里却没被使用；
- 更糟的是 fetchAdminApi 出错返回 null 不抛异常（745-762），switchCurrentModel 的 `.catch()` 提示“模拟模式”（1692-1694）永远不会触发——用户点了切换、看到标题变了，实际什么都没发生。
- 同理 loadConfigData 只请求 `/admin-api/settings`（1143），codex/hermes 下 404，“当前模型”永远显示 HTML 里硬编码的 `claude-sonnet-4-20250514`（L590/L643）——对这两个代理是错误信息展示。

**B6〔P1〕Token 过期后无全局 401 处理，页面退化成“假数据模式”而不是引导重新登录**
- token 8h 过期（server.js:74），过期后所有 API 401；fetch 拦截器只注入不拦截（dashboard.html:1336-1346）→ dashboard catch 后加载 mock 数据 + offline banner（1205-1210），用户看到的是“三个代理运行中”的假象加一条误导性横幅，而不是登录页。sessionStorage 方案放大了此问题。

**B7〔P2〕外部启动的代理“看得见停不掉”且无解释**
- isProcessRunning 有 lsof 兜底（server.js:365-372）能识别手动 `node proxy.js` 启动的代理并显示“运行中”；
- 但 stopProxy 只 kill allowedPids（630-634 `if (!allowedPids.has(pidNum)) continue`），外部进程必然 stop 失败，仅报"Failed to stop, process still running"。用户不知道原因是“非本面板启动”。至少应在返回体里说明并给出 PID。

**B8〔P2〕API Key 明文进 DOM + masked key 参与连通性测试**
- renderProviders 把完整 api_key 写入 `data-key` 属性（proxy-config.html:1308、1312），查看元素即可窃取，与 Cursor 代理 AES-256-GCM 加密存储的安全叙事矛盾；
- 测试按钮的 data-key 取自可能已被后端 mask 的值（如 `sk-1****`，codex-proxy/proxy.js:351-353 只回前 4 位），loadProviders 又用内存旧 key 回填（767-787）——key 在别处被修改后，“测试”必失败且用户无从排查。

**B9〔P2〕杂项**
- `isReadOnlyEndpoint`（server.js:134-138）定义后从未调用，死代码；且 `/api/status`、`/api/version`、`/api/env-check`、`/api/autostart`(GET) 均匿名可访问（705/1296/1331/1355），与 README“通配符认证绕过已修复”的安全口径不完全一致（env-check 会泄漏哪些 key 为空）。
- dashboard 的 showDemoBanner/hideDemoBanner 操作不存在的 `#demoBanner`（dashboard.html:1246-1259），死代码。
- appendLog 每写一条就全量读+写截断 5000 行（server.js:210-214），同步 IO 在请求路径上，高频转发时是 O(N)/条的瓶颈。
- refreshBalance 按 `data[index]` 数组下标对齐余额（proxy-config.html:1731），前后端供应商顺序不一致时会张冠李戴。

## 三、产品定位与核心价值

定位清晰：**“三个 AI 代理的统一控制台”**，dashboard 解决“活着吗”、config 解决“用哪个模型/哪家供应商”、logs 解决“出了什么事”，闭环成立。`tools/agent-proxy-switch` 对“单一所有者”问题的处理（切前验端口、绝不污染全局环境）体现了很好的运维判断力。

但有一个结构性缺口值得指出：agent-proxy-switch 之所以必须存在，是因为产品本身缺“**接线状态可视化**”——用户无法在面板上看到“codex 当前 base_url 指向谁”。建议把这个能力收编进 manager，做成每个代理卡片的“Agent 接线：→ proxy-rebuild / → cc-switch / → 直连”字段，一键切换，比独立 bash 脚本更符合产品化方向。

## 五、用户体验流程评估

- **首次使用**：首访引导设密码 + 强度指示器做得规范；但强度四级标签（弱/一般/良好/强，login.html:894）与 FUNCTIONS 宣称的 Weak/Fair/Good/Strong 四级对应混乱（classes 数组把 score 1、2 都标 weak，login.html:895）。首次设置复用 `/api/auth/login` 端点（login.html:994），意味着“谁先访问谁设密”，内网可接受但值得在文档明示。
- **日常操作**：启停乐观更新 + BroadcastChannel 同步是好体验；但 B7（外部进程停不掉）和B6（token 过期假死）是日常操作里最可能撞上的两个坑。
- **出错处理**：forwardProxy 的错误脱敏（server.js:937-946）把上游错误压成 statusText——安全上对，排障上过于激进：用户在 UI 上只看到 `"Internal Server Error"` 这类通用文案，具体哪个供应商挂了要去翻服务器 stdout（console.log 才有详细信息，appendLog 也只有 message）。建议脱敏保留错误码/类别，细节进需认证的日志页——日志页本来就是干这个的。
- **一致性瑕疵**：登录限流的前端倒计时（login.html:945-957）基于内存 attemptLog，与服务端 15 分钟窗口不同步，可能出现前端放行、服务端 429 返回英文报错，混在全中文界面里。

## 六、需求优先级评价与建议

已完成路线图（P0 安全 → P1 性能/体验 → Docker/Round-Robin）优先级判断基本正确；问题是**收尾不彻底**——大量“后端有、前端没接”的功能（history、fault、exportLogs、switch-model）说明迭代缺少一个“UI-端到端验收”环节。PROJECT-STATUS 宣称“剩余待办（无）”，与上述断头路直接矛盾。

**建议的下一步优先级：**
1. **P0**：修 B1（日志格式统一成 JSON 解析）、B2（密码重置指引改正文件路径）；
2. **P1**：接通 history/switch-model/exportLogs 三个断头路（后端都已就绪，纯前端工作）、全局 401 拦截跳登录、删除全部 mock 降级改为显式空态、修 SIGKILL 死代码；
3. **P2**：版本号与配置路径改为真实读取、fault 状态上 UI、外部进程 stop 给出解释性文案、把 agent-proxy-switch 的接线状态产品化进面板；
4. **流程建议**：给 FUNCTIONS.md 建立与代码同步的验收标准（每个宣称的功能标注验证方式），否则文档正在从资产变成负债。
