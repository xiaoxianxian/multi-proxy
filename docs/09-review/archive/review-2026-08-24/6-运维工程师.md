# proxy-rebuild 运维脚本字段级代码评审报告

评审对象：`install.sh`(635行)、`manage.sh`(454行)、`docker-compose.yml`、4个 Dockerfile、`tools/agent-proxy-switch`(259行)。以下所有结论均逐行核对过源码。

---

## 一、做得好的地方

1. **lsof 绝对路径规范执行到位**：`install.sh:47,285-288`、`manage.sh:41,229,264…`、`tools/agent-proxy-switch:63` 全部使用 `/usr/sbin/lsof`，与 CLAUDE.md 铁律一致；`multi-proxy-manager/server.js:336` 也定义了 `const LSOF = '/usr/sbin/lsof'`。全仓库无违规。
2. **NO_PROXY 铁律合规**：对 install.sh/manage.sh/compose/Dockerfile/tools 全文扫描，无任何 `launchctl setenv NO_PROXY` 写法；plist（install.sh:382-386）只注入 `PATH`，未污染全局环境。历史事故教训已固化进代码注释（agent-proxy-switch:18-25）。
3. **端口就绪采用轮询而非盲等**：`manage.sh:47-59` 的 `wait_for_port`（200ms 步进、可配超时）优于 install.sh 里固定 `sleep 1`（install.sh:241 等）。
4. **切换工具设计成熟**：`agent-proxy-switch` 有 `set -eo pipefail`(:43)、写前备份(:85,:110)、幂等短路(:84)、切前端口防死链校验(:184-188)、按 agent 隔离不误伤。
5. **Cursor 多阶段构建**：`Dockerfile.cursor:1-23` builder/runtime 分离，runtime 只拷 `dist` + 生产依赖。
6. **`.dockerignore` 排除了 `.env`**（根级），避免密钥进镜像层。

## 二、严重问题（Bug）

### B1. LaunchAgent `KeepAlive=true` + 一次性脚本 = 无限重启风暴 ⭐最严重
`install.sh:374-377` 生成的 plist 同时设 `RunAtLoad` 和裸 `KeepAlive=true`，而 `ProgramArguments` 是 `bash manage.sh start`——该脚本启动完服务后**正常退出**。launchd 视"退出"为崩溃，会以约 10s 节流周期无限重拉 `manage.sh start`。每次重拉虽因端口已占用而走 `print_warning` 分支（manage.sh:79-82），但警告文本持续写入 `StandardOutPath`（install.sh:378-381 指向 `~/.multi-proxy-manager/logs/stdout.log`），**该文件无上限增长且无人清理**。修复：改为 `KeepAlive = {SuccessfulExit = false}`，或让 plist 直接前台运行一个常驻进程。

### B2. `set -e` 使大量错误处理分支成为死代码
- `install.sh:14` 有 `set -e`，则 `install_cursor` 中 ：142 `(cd … && npm rebuild …)` 失败时脚本**立即终止**，:143-156 的降级重装分支永远不可达；:160-162 的 `BUILD_EXIT=$?` 同理是死代码。
- `manage.sh:2` 有 `set -e`，则 `start_cursor` :153 的 rebuild 失败直接退脚本，:154-167 降级逻辑同样不可达；`:134-135` 的 `BUILD_EXIT=$?` 也是死代码。
- `manage.sh:11-15`：`set -e` 下 `mkdir -p` 失败即退出，`if [ $? -ne 0 ]` 永假；且此处调用 `print_error` 发生在其定义（:36）之前，真触发也是 `command not found`。

### B3. compose 用空命名卷覆盖 `/app`，镜像更新后跑旧代码
`docker-compose.yml:13` `codex-proxy-data:/app` 与 ：29 `hermes-proxy-data:/app`：首次启动 Docker 把镜像 `/app` 内容拷入空卷，之后**每次重新 build 镜像，容器仍挂旧卷里的旧代码**——升级即失效，这是典型反模式。这两个卷应删除。

### B4. 卸载完整性：README 已知问题 #2 属实
`uninstall_launchd`（install.sh:224-231）只处理 `com.multi-proxy-manager.plist` 一个文件，不扫描 `com.codex.*` / `com.xiaoxian.*` 遗留 plist。README:196-200 的描述准确。实测当前 `~/Library/LaunchAgents/` 已无这两类残留（本机已手工清过），但脚本层面缺陷仍在——换机重装必踩。另外卸载也不清理 `~/.multi-proxy-manager/` 数据目录和两处日志目录。

### B5. agent-proxy-switch 校验不对称：切到 cc-switch 前不验端口
`switch_one` 中 codex→proxy-rebuild 有 `port_listening $CODEX_PORT` 防死链(:184-188)，但 codex→cc-switch 分支(:180-182)**没有**对应的 `port_listening $CC_SWITCH_PORT` 检查——cc-switch(15721) 未启动时照样写入 base_url，制造死链，违背自家"不死链"原则（:29-30）。

### B6. 按 PID 杀端口的误伤风险
`manage.sh:229-240` 与 `install.sh:285-288` 用 `lsof -ti :$PORT` 取 PID 后 kill：若目标服务死掉后**端口被无关进程抢占**（或用户另起进程占用同端口），脚本会把无辜进程杀掉。install.sh 更是直接 `kill -9` 无优雅期，与 CLAUDE.md 宣称的"SIGTERM→500ms→SIGKILL 两阶段"（server.js 内实现）不一致——shell 路径没有两阶段。建议 kill 前 `ps -p $pid -o command=` 校验进程身份。

## 三、中等问题

### M1. 日志轮转全面缺失（属实）
三处日志均无轮转机制：
- `$SCRIPT_DIR/logs/*.log`（install.sh:159,240,250,270,280；manage.sh:86,114,177,205）追加写、无大小上限；
- `~/.multi-proxy-manager/logs/stdout.log|stderr.log`（install.sh:378-381）——叠加 B1 重启风暴后增长最快；
- compose 未配置 logging driver 上限（默认 json-file 不限尺寸）。
`manage.sh:300-334` 仅 `tail -50/-20` 展示，治标不治本。建议：plist 加 `EnvironmentVariables` 配 NODE 日志库轮转，或 compose 设 `logging: {options: {max-size: "10m", max-file: "3"}}`，或部署 newsyslog 规则。

### M2. Docker 化质量问题
- **零 healthcheck**：4 个 Dockerfile 与 compose 均无 HEALTHCHECK（已 grep 确认计数为 0），`depends_on`（compose:62-65）只保证启动顺序不保证可用性。
- **端口暴露到所有网卡**：compose:8,24,40,55 全是 `"18790:18790"` 形式，代理（含 API Key 能力）对局域网开放；应写 `127.0.0.1:18790:18790`。
- **docker.sock 挂载 = 宿主机 root 等价权限**（compose:61）：manager 有 Web 登录界面，一旦认证被绕过/弱密码，攻击者可直接经 sock 控制宿主。至少应在 README 标注威胁模型，理想方案是用 socket proxy（如 tecnativa/docker-socket-proxy）收敛 API 白名单。
- **全部容器以 root 运行**：4 个 Dockerfile 均无 `USER` 指令。
- **`npm install` 而非 `npm ci`**：Dockerfile.codex:8、manager:8、cursor:8,23——即使有 lockfile（`package-lock.json*` 可选 glob 说明 lock 可能缺失）构建也不可复现。
- **运行时镜像带编译链**：`Dockerfile.cursor:17` runtime 层装 `g++ make`（better-sqlite3 有 linux prebuild 时纯属浪费，单这一项多几百 MB）；`Dockerfile.hermes:5` 装 lsof、`Dockerfile.codex:5` 装 lsof——IS_DOCKER 模式下 server.js 走 `docker inspect`，容器内根本用不到 lsof。
- **build context 过大**：compose `context: .`（各服务 :4,20,36,51）把整仓当上下文，而 `.dockerignore` 的 `node_modules`/`dist` 无前导 `/` 时仅匹配根目录，`codex-proxy/node_modules` 等子目录依赖仍会被发送给 daemon。
- **env_file 强依赖**：compose:10,26,42,57 任一 `.env` 缺失则 `up` 直接失败，无缺省提示（install.sh 会创建 .env 但 Docker 路径用户未必先跑 install.sh）。

### M3. 开机自启可靠性
- 除 B1 外：`setup_autostart` 未 `mkdir -p ~/.multi-proxy-manager/logs`（install.sh:378-381 引用的目录），launchd 不建父目录，目录不存在时作业日志丢失甚至影响启动。
- `launchctl load/unload`（install.sh:227,391,399）是已废弃 API，现代 macOS 应迁移 `bootstrap/bootout gui/$UID`。
- nvm 版本探测 `ls -d … | tail -1`（install.sh:342）：`ls` 结果排序下取"最大版本号字符串"，遇到 Node 9 vs Node 10 这类字典序陷阱会选错（9 在 10 后面）。建议 `sort -V`。
- plist 未设 `NO_PROXY=127.0.0.1,localhost,::1`——CLAUDE.md 说"如确需绕过 localhost 只在自身 plist 里设"，当前连这个安全形态也没配，代理自访问 manager 回环是否走系统代理取决于环境，属可选加固项。

### M4. 双份真相源
install.sh:235-283 自带一套 start_*/stop_*/show_status（固定 sleep 1、kill -9），manage.sh 另有一套（wait_for_port、两阶段 kill）。行为不一致且端口/路径常量重复定义（CLAUDE.md 要求与 agent-proxy-switch "务必保持一致"，靠人肉同步）。install.sh 的启停命令应薄封装 `bash manage.sh`（--restart 分支 :576-578 已经这么做了，更显得 --start/--stop 是冗余异构实现）。

## 四、轻微问题

- `CODEx_PORT` 命名大小写混乱（install.sh:36、manage.sh:24）。
- install.sh:592 `$0 --stop` 未加引号，路径含空格即崩（:576-578 用了 `bash "$0"` 是对的，风格不统一）。
- install.sh:95 `npm install --production` 已废弃，应用 `--omit=dev`。
- install.sh:117 `pip3 install` 直装系统 Python：Homebrew Python 目前不带 EXTERNALLY-MANAGED 标记所以能跑，但无版本锁定/venv 隔离，属脆弱点（requirements.txt 本身倒是锁了版本，好）。
- install.sh:444-447 用 `grep -q "1"` 匹配选项，输入 "14" 会同时命中 1 和 4。
- install.sh:533-535 API Key 检查硬编码 `DEEPSEEK/MOONSHOT/AGNES` 三键，新增供应商需手改脚本；hermes-proxy 若无 requirements.txt 则静默跳过安装(:115)。
- `manage.sh:303-333` `show_logs` 对未知服务名静默无输出，缺 `*)` 分支。
- agent-proxy-switch:85/:110 每次切换留一个时间戳备份文件，无清理策略，长期累积。
- agent-proxy-switch:97 写 TOML 时丢原缩进（`f'base_url = "{new_url}"'`），TOML 语义无害但 diff 不友好。
- Dockerfile.cursor CMD 是 `node dist/index.js start`(:29)，manage.sh:177 用 `dist/server/start.js`，package.json start 又是 `dist/index.js`——三个入口并存，易混淆。

## 五、结论

项目在**安全纪律层面（lsof 绝对路径、NO_PROXY 铁律、防死链意识）执行力很好**，历史事故教训确实固化成了代码约束。但运维可靠性层面短板明显：B1（KeepAlive 重启风暴）、B2（set -e 死代码）、B3（卷覆盖 /app 导致升级失效）是会在真实使用中爆雷的缺陷；日志轮转缺失与 README 描述一致属实；卸载残留问题 README #2 描述属实但未修。优先修复顺序建议：B1 → B3 → B2 → B5/B6 → M1/M2（healthcheck + 127.0.0.1 端口绑定 + sock 收敛）。
