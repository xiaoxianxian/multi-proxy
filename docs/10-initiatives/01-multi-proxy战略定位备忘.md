# multi-proxy 战略定位备忘（一页）

> 用途：对外写作素材 / 内部对齐文档。最后对齐：2026-09-25，与用户确认。
> 数据可回源见末节。

## 一句话定位
multi-proxy **不是 AI 底层基础设施**，而是**面向业务 / 用户、直接交付价值的「集成 / 加速层」**——把技术类基础设施当发动机嵌入，封装成可组合能力。

## 三层关系（对照阿里技术文章）
- **① 技术类基础设施**（阿里六开源 ROLL / RTP-LLM / Atrex Kernel Agent / OpenSandbox / Open Agent Auth / OpenCodeReview 等）：发动机 / 加速器，需开发者用以造应用与 Agent。
- **② multi-proxy（本项目真实位置）**：集成 / 加速层。把底层基础设施当引擎嵌入 → 封装成可组合能力；**一切皆插件**，能力可单用或组合，接入 dsh / code 等 Agent 生态，也可组合后独立把各 Agent 当「功能」调用解决场景问题。
- **③ 业务 / 用户场景**：直接交付价值，构成壁垒。

三者**互补不竞争**：技术基建需开发者使用才能发挥价值；multi-proxy 直接拿来嵌入，使其更健壮好用。

## 壁垒来源（纠正「离用户近 = 壁垒」）
壁垒来自 **集成深度 + 组合编排 + 切换成本**，不是「离用户近」本身。单点工具可被替换、无壁垒；组合成解决方案才有粘性。

## 愿景 vs 现状（对外讲必须分清）
- 愿景：健壮的引擎 / 加速层。
- 现状（9/23 七角色评审）：仍是薄代理 ——
  - C0-1 局域网匿名泄露真实 token（鉴权未立）
  - C0-3 成本 / 模型数字来自 `Math.random()`（可观测是假的）
  - C0-6 测试覆盖率 0%、无 CI（验证闭环失效）
- 结论：想当「发动机」，须先按评审 §5 第一批补鉴权 + 验证。

## 护城河边界（须守住）
永远待在基础设施之上、贴业务场景做组合；**不下沉抢「做引擎」的活**（防厂商爬栈：Open Agent Auth / OpenSandbox 等可能自己长出编排层）。

## 一切皆插件的落地锚点
该哲学 = 代码里的 **L2 多 agent 编排层**。评审发现 L2 当前是纯旁路（MCP 面读不到活跃 registry、`decompose`/`orchestrate` 经 HTTP 不可达、`pluginCaps` 恒空）。最小改造计划见同目录《02-L2热路径改造计划.md》，≈3 处核心改动即可让「组合 agent 当功能调用」从 PPT 变真能力，且不破非侵入铁律。
