# L2 接进热路径 · 最小改造计划（仅方案，未落码）

> 目的：把 multi-proxy 的「一切皆插件 / 把各 agent 当功能调用解决场景问题」哲学，从设计态变成运行态。
> 约束：不破非侵入铁律——门控默认关、shadow 默认开、不改任何现有数据面行为。
> 来源：9/23 七角色评审 · 架构师报告 A3（A3.1–A3.3、N3）+ 总报告 §5 第二批 #5。评审文档绝对路径：`/Users/xiaota/WorkBuddy/2026-09-14-09-45-18/multi-proxy-评审-2026-09-23/1-架构师.md` 与 `.../00-总报告.md`。
> 本计划只描述「改什么 / 在哪 / 为什么 / 怎么验证」，不写实现代码。

## 一、现状事实（架构师实测，均附 file:line）

- **registry 分裂**：L2 全仓有 **4 个 `AgentRegistry` 实例**——`routes/mcp.js:31`(+seed)、`routes/registry.js:19-20`(不 seed)、`l2/mcp-server.js:71/494`(+seed)、`l2/savings-gateway/gateway.js:87`(+seed)。MCP 面用的是「自己那份」→ 新建 agent 在 MCP 工具面不可见（P2-1 已证实）。
- **sync/async 工具面断裂**：HTTP 面永远走同步 `callTool`/`handleMessage`（`routes/mcp.js:87,100`），而 `decompose`/`orchestrate` 只在异步分派里（`callToolAsync:253-315` / `handleMessageAsync:365-400`）→ 经 HTTP 恒返回 `-32602 Tool not found`（P2-2 已证实，且 `orchestrate` 后端根本没报）。
- **route() 隐藏副作用**：`l2/route-engine.js:124` 的 `decision.execution` 是 fire-and-forget 且全仓 0 读取者（N3）；`_execute` 在无 executor 时退化为 `{status:'queued'}`，一旦有人按二期计划注入 executor，`route()` 会先 fire 一次、调用方再 execute 一次 → 真上游被调两次。
- **plugin 面是空集**：`PluginRuntime` 生产仅被 `new`（`routes/mcp.js:38`、`l2/mcp-server.js:74,497`），全仓无一处生产代码 `register(...)`/`loadFrom(...)` → `route-engine.js:66` 的 `pluginCaps` 恒 `[]` → 「一切皆插件」候选来源在生产永久空集（A3.1）。

## 二、改造步骤（按依赖排序）

### Step 1 · registry 单例注入（A3 #1 + #6）
- **改什么**：`routes/registry.js` 导出单例实例；`routes/mcp.js:26-43` 改为注入该实例，不再 `new AgentRegistry()`。`seedDefaultProfiles` 仅在 `registry.count() === 0` 时执行（函数本幂等，`mcp-default-seed.js:46`）。
- **连带**：把 `l2/savings-gateway/gateway.js:87` 也纳入同一注入链，否则修完仍有第 4 份、「当前有哪些 agent」仍有第 2 个答案。
- **为什么**：只改「看哪份内存」，零副作用、零外部写入，不破铁律。
- **验证**：manager 起 `PROXY_L2_MCP=1`，`POST /api/registry/agents` 与 `GET /api/mcp` 看到的 agent 数量一致；新建 agent 后 MCP 工具面立即可见。

### Step 2 · HTTP 面统一走 async 分派（A3 #2）
- **改什么**：`routes/mcp.js:82-109`，`/api/mcp/call` → `await s.callToolAsync(...)`；`/api/mcp/rpc` → `await s.handleMessageAsync(...)`。同步入口保留给 stdio 兼容。
- **为什么**：`callToolAsync` 对非 async 工具委托回同步 `callTool`（`mcp-server.js:314`），行为超集、不回归。
- **验证**：`POST /api/mcp/call decompose` / `orchestrate` 返回 200 且有真实拆解 / DAG；不再 `-32602`。

### Step 3 · 修误导性错误数据（A3 #3）
- **改什么**：`l2/mcp-server.js:204-216`，`-32602` 的 `available` 改为 `s.listTools().map(t => t.name)`，让报错里的工具列表真实。
- **验证**：调不存在工具时，`available` 等于 `tools/list` 全量，不再缩成 5 个 adapter。

### Step 4 · route() 纯决策化（N3，防双执行）
- **改什么（二选一）**：① 删除 `decision.execution`，`route()` 回归纯决策函数，执行彻底交给调用方；② 拆成 `route()`（纯决策）+ `routeAndExecute(): Promise`（显式异步）。并补一条断言「`route()` 在非 shadow 下不得产生任何副作用」。
- **验证**：`shadowMode` 下多次调 `route()` 不产生任何上游调用；`savings-gateway` 注入 executor 后（`gateway.js:85,139`）不出现双执行。

### Step 5（让「一切皆插件」真活）· plugin 面 bootstrap（A3 #5）
- **改什么**：新建 `lib/l2-bootstrap.js`，manager 启动时把 `l2/adapters/*.js` 注册进 `PluginRuntime`。adapter 是普通对象，`register` 不改任何 agent 文件（不破铁律①）。
- **验证**：`route-engine.js:66` 的 `pluginCaps` 非空；新增 adapter 后无需改 registry 文件即被编排识别。

### Step 6（可选，GOD agent 友好）· MCP 资源面（A3 #4）
- **改什么**：`l2/mcp-server.js:333-400`，补 `resources/list`（活跃 agent 列表）+ `resources/read`（profile 只读视图）。`initialize` 已声明 `resources:{}`（`:100`）。
- **为什么**：纯只读，比暴露 `tools/call` 更贴合非侵入铁律，是「让 agent 看见活跃注册表」的最优形态。

## 三、明确划界（不在本计划范围）

- **数据面 inline 路由不做**：L2 仍定位为「控制 / 组合面」，各 proxy 自管请求路由（`codex=findProvider`、`cursor=findProviderConfig`）。不把 L2 塞进每条请求链路——这是 A2 的「诚实收敛」方案（成本≈0），避免把本计划变成重写数据面。
- **鉴权边界（A4 / C0-1）不做**：`routes/sessions.js` 匿名 CRUD、`L2` 面鉴权不一致 → 属总报告 §5 第一批安全项，单独修，不在此混。

## 四、完成判据（给 Hermes 的验收清单）

1. 门控默认关、shadow 默认开，零现有行为回归（6 个门控 HTTP 仍 403）。
2. `decompose` / `orchestrate` 经 HTTP 可达且产出真实（非 `-32602`）。
3. MCP 工具面反映活跃 registry（新建 agent 可见）。
4. `pluginCaps` 非空，「一切皆插件」从空集变真。
5. `route()` 无隐藏副作用；`savings-gateway` 注入 executor 后无双执行。

> 说明：Step 1–3 是「≈3 处改动让 L2 从旁路变可调」的核心（对应总报告 §5 #5）；Step 4–6 是让「组合 / 插件」语义真正成立的加固项，可分批合入。
