# 外部 harness 接入底座约束（single egress）

> 状态：2026-10-03 外部对照（openrig）产物。**结论已按代码锚点回源核实，未实测运行。**
> 读者：任意 agent / 人类。读完应知道两件事——**底座必须当唯一出口**，以及**接一个新 harness 进来要过哪三条**。
> 关联：`路由能力矩阵与开发建议-2026-09-30.md`（P1-3 复杂度 gating）、`docs/03-architecture/architecture.md`、`l2/EXTERNAL-OPTIONS-REGISTER.md`

---

## 零、一句话结论

**任何访问模型的 harness（含第三方 rig 类框架拉起来的座席）必须经 multi-proxy 出网；底座不是"可选加速器"，是唯一出口。**

凡自带 provider 选择权的接入方式（直连、复用已登录 session、CLI 内建 endpoint 配置），路由门对其**全部失效**，且失效是静默的——流量照跑，账目照空。

---

## 一、为什么要钉死这条（理由，不是偏好）

multi-proxy 的四个能力都以「流量经过我」为前置：

| 能力 | 落点代码 | 流量不经过就怎样 |
|---|---|---|
| complexity 路由门 | `l2/route-engine.js:139`（`tierMatch` 只看显式声明 `modelTier` 的 profile） | 该走 small 的活跑了 large，**省钱的那一层根本没参与** |
| 省钱统计 | `l2/savings-gateway/`（`gateway.js` / `server.js` / `cost-watchdog.js`） | 统计漏项，省了多少算不出来 |
| failover / 韧性 | `l2/circuit-breaker.js` / `rate-limiter.js` / `health-monitor.js` | 上游挂了没有熔断，重试点落在裸 provider 上 |
| Portico 侧定价 | Portico 派活单 `complexity` 字段 → 走底座 → 落到 `mapTier` | **Portico 定的档位对这个 agent 一点用都没有**（见 `03-架构设计.md` 合约定稿第 5 条与 `04-待拍板.md` #8） |

**漏统计不是丢一条日志，是整层治理对这批流量归零。** 这就是为什么它是约束而不是建议。

### 反例：openrig 的做法直接踩这个雷

外部对照项目 `mvschwarz/openrig`（Apache-2.0，2026-04-01 建，2026-10-03 push，4558 stars）的 kernel **自己从已登录的 provider 里独立选模型**，不经过任何代理。按它的默认形态跑，每个座席的流量整个绕过底座。

→ 正确的接法是反过来的：**openrig 每个座席的 CLI 背后挂 multi-proxy，底座是唯一出口。** 这一点已回写进 Portico 的 `04-待拍板.md` #8 前置说明（同一个 concern 的两侧）。

### 反例二：ccteam 绕过，而且自己记一本（2026-10-04 补）

外部对照项目 `firstintent/ccteam`（MIT / Rust / 2026-05-04 建 / 2026-09-25 push，约 378 stars 为二手、本文不采信）比 openrig **更贴这个雷**——它**不造 agent**，直接 spawn 机器上现成的 vendor CLI 并让各 CLI 用**自己的登录态**出网：README「Install」段要求先 `install and authenticate at least one`，Claude Code 走 `claude auth login`、Codex 走 `codex login`、DSH 走 `DEEPSEEK_API_KEY`，并明写 "sitting on `PATH` never counts as logged in"。

回源核验：README 全文 280 行，`grep -inE "base[-_]?url|endpoint|proxy|api[_-]?key"` **只有 2 处命中**，分别讲「HTTPS 反代要连伴生监听器一起反代」和「DSH 用 `DEEPSEEK_API_KEY` 或 DSH Settings → Models 配置」——**没有任何一处支持把 vendor 端点改指到本地代理**。→ 按默认形态跑，每个座席流量整层绕过底座。

🔴 **ccteam 比 openrig 多一条病：双账本。** openrig 是「账目照空」，ccteam 是**绕过底座的同时自己记账**——它自带 cost ledger（Team page 每笔委派挂钱）、`cost pill with daily budget caps`、`flow run --budget <n>`、`--max-cost`、`pre-agent` hook 里下发的 live per-harness quota map。

→ 于是 `l2/savings-gateway/` 与 ccteam 账本会**同时存在且口径不同**（它记 vendor 用量，底座记走过这层省了多少）。**接之前先定「谁出账」**：推荐 **savings-gateway 出账、编排层只引用不记账**，否则两边永远对不上，#8 的偏移率表也拿不到一致数据。

→ 判据 ① 判什么，看得出差别：对 openrig 问「端点配哪」，对 ccteam 还得**加问一句「它有没有自带预算/账本，有的话那本账归不归编排放」**。

## 一之二、正例（DSH）：官方给的是缝，所以不需要代理网关（2026-10-04 补）

前面两个反例都是「端点改不动」的人。**正例同样重要，否则判据会变成「一律钉死」而不是「先找缝」。**

`DSH` ＝ `deepseek-ai/deepseek-harness`，**DeepSeek 官方开源 harness（MIT，不是第三方插件）**，desc「Everything is a Plugin」。它**给了两处端点缝**：

| 缝 | 形态 | 证据 |
|---|---|---|
| 环境变量 | `export DEEPSEEK_BASE_URL=http://127.0.0.1:<port>/v1` | 官方 SDK 文档 `deepseekharness.io/python-sdk/` 原话「Uncomment the base URL only when your endpoint is a compatible proxy rather than DeepSeek's own」，示例值直接是 **`http://127.0.0.1:8000/v1`** |
| 配置文件 | `llm-pi-ai.providers.<id>.baseURL` ＋ `apiKeyEnv`（key 走环境变量、不落 yaml） | 本机生效配置 `~/.dsh/profiles/desktop/cordis.patch.yml`，同行还有 `agnes`（`baseURL: https://apihub.agnes-ai.cn/v1`）、`ollama`（`http://localhost:11434/v1`）、`curator`（`http://127.0.0.1:18795/v1`） |

**本机配置入口的确定过程**（只读扫描，别再找错文件）：`~/.dsh/settings.yaml` **不存在**（只有 `settings.yaml.imported` 与 `.dsh.bak/`）；`~/.dsh/profiles/desktop/cordis.yml` 自述「the tree is composed as patches… **Edit cordis.patch.yml, not this file**」→ **桌面端实际生效的是 `cordis.patch.yml`。**

🔧 **顺带订正一条上一轮记错的路径结论**：此前写「DeepSeek 官方 base_url 不带 `/v1`」是不完整的。`api-docs.deepseek.com` 原文：「出于与 OpenAI 兼容考虑，也可以将 base_url 设置为 `https://api.deepseek.com/v1` 来使用，但注意，此处 v1 与模型版本无关」。→ **带 `/v1` 与不带都合法，本仓库 `providers.sample.json` 现有 `https://api.deepseek.com/v1` 是对的，不要改。**

条款侧也核过：DeepSeek 开放平台服务协议英文原文**无禁止代理 / 中继 / 转发 / 改 endpoint 条款**（只有 2.2 key 自保管、7.2 违约处置）。个人自用「自己的 key + 本机代理 + 转发官方端点」不落在禁止项。

→ **接 DSH 只改一处端点，不装 `dsh plugin add`、不引入 ccteam 那种 `0.0.0.0:7331` daemon。**

### 一之二之二、本机 DSH 现状全貌（2026-10-04 只读扫描）

缝是开着的，但**开着 ≠ 在用**。把现状摆全，别只看配置里写了什么：

| provider | 端点 | 走底座？ | 备注 |
|---|---|---|---|
| `agnes` | `https://apihub.agnes-ai.cn/v1`（key 走 `AGNES_API_KEY`） | ❌ **直连外网** | **当前默认 provider** |
| `ollama` | `http://localhost:11434/v1` | n/a | 本来就是本地模型，绕过底座是对的 |
| `curator` | `http://127.0.0.1:18795/v1` | ✅ 过桥 | 模型 `agnes-3.0-flash` + `deepseek-v4-flash` |

`llm-pi-ai` 段下另有 `agent-default-model`：**`provider: agnes` / `model: agnes-3.0-flash`** —— 即 DSH 桌面端发请求的默认路径**不经过底座**。

🔴 **`curator` 不是生产 provider，是 A/B 实验的 B 组入口。** `tools/dsh-saving-ab.sh:6-8` 自述：「A 组 = dsh 不开 curator：请求直连 18790（multi-proxy 的 codex-proxy），桥不在路径上。B 组 = dsh 开 curator：请求过桥 18795（上游同样是 18790），桥做 rewrite ⇒ **唯一变量是「桥在不在路径上」**，A/B 可归因。」改它之前先记下这条基线，别当成实验组配置随手动。

🔴 **底座此刻压根没在跑。** 2026-10-04 07:2x 只读探测：`launchctl list` 无 multi-proxy / token-policy-bridge 条目，`18790` 与 `18795` 均不响应（`/health` 空返回）。⇒ **任何指向底座的 DSH 配置当下都是死配置**，改配置之前，先解决「底座怎么起来、起来后能不能长期住」这个前置。

⚠️ **桥（18795）不能当 DSH 的默认目标。** 维护者 2026-10-02 定调「不要常驻，本机还跑着本地模型，对内存敏感 ⇒ 按需加载」（`tools/bridge-launchd.sh:3-10`）。DSH 桌面端是会随时发请求的常驻客户端，若默认指 18795，桥没起时 DSH 直接失败。**默认目标应指底座主进程 18790；桥是可选的省钱增强层，不是接入必需层。**

→ **落地顺序（不要跳步）**：起底座 → 验 18790 通 → 才谈改 DSH 默认 provider。桥的启停在默认路径之外，属于省钱优化项。

### 一之二之三、DSH 底座接入：**已执行**（2026-10-04 维护者 signoff 后落地）

**前置（已完成）**：改动前 `launchctl list` 无 multi-proxy 条目、18790 不响应 ⇒ 只改配置是无效动作，第一件事是把底座拉起来。启动方式：`bash ./manage.sh start`（单进程即可，会起 codex-proxy 18790 / hermes 18793 / cursor 18794 / manager 18792；内存敏感时按 `manage.sh stop` 关掉用不上的那几支）。

**改动（已完成，全仓 diff 只有一行）**——`~/.dsh/profiles/desktop/cordis.patch.yml:13`：

```diff
       agnes:
         apiKeyEnv: AGNES_API_KEY
         api: openai-completions
-        baseURL: https://apihub.agnes-ai.cn/v1
+        baseURL: http://127.0.0.1:18790/v1
         models:
         - id: agnes-3.0-flash
```

默认 provider（`agent-default-model` = `agnes` / `agnes-3.0-flash`）与 models 白名单**一行未动**。选它而不是「改默认 provider 指 `curator`」的理由：`curator` 挂的是桥 18795 且默认模型 `deepseek-v4-flash`，换过去桌面端体感会变；**换端点不换模型，日常体感才不变。**

**验证（按完成标准逐条，缺一不算）**：

| # | 标准 | 状态 |
|---|---|---|
| 1 | 底座进程在跑 + `/health` 有返回 | ✅ 已过（`lsof -iTCP:18790 -sTCP:LISTEN` 有 PID；`/health` 返回 `{"status":"healthy",...}`） |
| 2 | 端点实测 200 | ✅ 已过（`POST /v1/chat/completions` 模型 `agnes-3.0-flash` → **HTTP 200**，返回内容正常）。`--noproxy '*'` 必带，不加会打到 Clash 上看到「upstream connect failed」 |
| 3 | **agent 侧真实发一次** | ⏳ **待维护者在桌面端做**：开一个新会话发一句话，回复正常**且 `logs/codex-proxy.log` 里有这条**。前两条只证明底座自己活着，第 3 条才算接入完成 |

⚠️ 第 3 条的两个已知风险（如实记，不做假承诺）：

- **GUI 拿不到环境变量**：`apiKeyEnv: AGNES_API_KEY` 是环境变量，dsh 桌面端由 Dock/launchd 起进程、外部注入不了（`agent-proxy-switch` 注释自述「GUI 常驻型做不到零写入」）。实测第 2 条 curl **不带任何 key 也返回 200**，说明底座侧不鉴该 key，推测由底座自有凭据打上游；但若桌面端因此拒绝出参，症状是「桌面端报错」而非「底座报错」，排查方向别走反。
- **桌面端要重启才读新配置**：Electron 应用不会热读 `cordis.patch.yml`。

##### 🔴 可逆性硬要求（维护者 2026-10-04 定：代理必须可关，关掉回到 agent 自有配置）

**这是接任一 agent 的前置条件，不满足不许接入。** 三条：

1. **开启前先备份**：改 `cordis.patch.yml` / agent 自有配置的**同一条命令里**先 `cp` 出一份带时间戳的备份，备份路径写进本文档。
2. **回滚必须一行可还原**：回滚方式只认「换回备份文件」或「改回原 URL」二选一，不许需要手工拼 yaml。
3. **不许留死链**：关掉代理后 agent 必须能回到它**自己原来的** endpoint。现场踩过的坑——`agent-proxy-switch` 注释里写明 `off` 用的是 **undo（记状态）而不是猜「直连是谁」**，因为 codex 的原生直连是 `api.openai.com`，工具不知情，**猜错就会把 agent 送到一个没账本的地方**。改配置前先确认这条链路有没有 undo 语义，没有就别动。

本机可逆现状：`tools/agent-proxy-switch` 已具备 dsh 的 `curator` / `off` 一对（per-agent 状态文件 `~/.multi-proxy-manager/curator-switch-state-<agent>.json`，`off` = undo 到切前 owner），**但它只覆盖「换默认 provider 指桥」「undo」，不覆盖本次的「agnes 改 baseURL 指底座」** ⇒ 本次靠手工备份兜底，命令见下。

**回滚（一行，已验证可用）**：

```bash
cp ~/dsh-cordis.patch.yml.pre-18790-20261004-073606 ~/.dsh/profiles/desktop/cordis.patch.yml
```

备份文件：`~/dsh-cordis.patch.yml.pre-18790-20261004-073606`（改前自动记录的原值 `https://apihub.agnes-ai.cn/v1`）。回滚后需重启 DSH 桌面端。

### 一之二之四、怎么验证 GUI 型 agent 真接上了（2026-10-04 补）

#### 🔴 核心教训：成功无法证明，只能证伪

底座只是**转发到同一家厂商**，所以「桌面端能正常说话」**既可能过底座、也可能还在直连**——这两个状态在行为上完全一样。**拿「能回话」当验收 = 假阳性。**

本机实测坐实这点：向 18790 发 2 次真实 POST（`agnes-3.0-flash` 均 200），`logs/codex-proxy.log` **增量 0 行**（底座不记请求日志）；`18792/metrics` 返回的是管理面板 HTML 不是 API；DSH 侧 `session.v4.jsonl.zstd` 只记 session 元信息与权限策略，**不记 HTTP 请求**。⇒ **所有「看日志有没有记录」的验证路线都是死路**，只剩一条硬判据。

#### 第一道判据（构型层，可自动验证，不用碰 GUI）：patch 是否真的合成进配置树

断底座是**运行时**判据，但第一道可以更早、更省：直接问 DSH「你合成出来的最终配置里 baseURL 是什么」。

CLI 在桌面端包里，路径 `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`（`bin/dsh` 是 shim，最终 exec Electron 的 `cli.js`）。两条已知限制：

1. `dsh --profile desktop --dump-config` **会被拒**：`error: profile "desktop" is managed exclusively by the Electron application`——desktop profile 由 Electron app 独占，CLI 摸不到。
2. 绕法：挑一个中立 profile，用 `--patch` 把我那份 patch 叠上去再 dump（`--patch` 可重复，叠在 profile 层之后）：

```bash
dsh --profile web --patch ~/.dsh/profiles/desktop/cordis.patch.yml --dump-config \
  | grep -nE "baseURL|18790"
```

2026-10-04 实测：合成树第 85 行 `baseURL: http://127.0.0.1:18790/v1`，同树里另有 `ollama → http://localhost:11434/v1`、`curator → http://127.0.0.1:18795/v1` 三个 provider 并存。

→ **这条证明了什么**：patch 的 YAML 结构合法、没被静默丢弃、值确实进树 ⇒ 桌面端加载时**不会因为 patch 解析失败而回退到直连**。它排除的是「配置链断了」这一类假阴性。
→ **它证明不了什么**：流量是不是真的从桌面端打过来。那要靠下面第二道。

#### 第二道判据（运行时）：断底座，agent 应该立刻哑

| 现象 | 判定 |
|---|---|
| 停掉底座后桌面端发话 **报错 / 转圈 / 无响应** | ✅ 铁证，确实走底座 |
| 停掉底座后桌面端 **照常秒回** | ❌ patch 没盖住 bundle 默认值，还在直连，假阳性 |

#### 🔑 免 GUI 的运行时验证：`dsh headless "<prompt>"`（2026-10-04 二轮实测确认）

上面写的是「去桌面端手动发一句话」。实测发现 **没必要开 GUI**，DSH 自带 headless profile，一次请求走完整链路（provider → baseURL → 模型），输出直接打 stdout：

```bash
# 用 desktop 那份 patch 起一次 headless（CLI 可被 --patch 叠任意 patch）
dsh headless --patch ~/.dsh/profiles/desktop/cordis.patch.yml "只回两个字：好嘞"
```

实测（每次约 8-12 秒）：

|底座状态|命令输出|判定|
|---|---|---|
|18790 在|`好嘞`|链路通|
|18790 停|`dsh: TRANSPORT: Connection error.`|**与桌面端报错原文逐字一致**，证明确实走底座|

⇒ 断底座 + headless 就是第二道判据的完整可执行版，**不再依赖手动去 GUI 发话**（那件事还容易被维护者当成「我发完没反应」吵一轮）。

注意 CLI 参数形态：`dsh headless --patch <path> "<prompt>"`（`--profile` 那套对 desktop 无效，desktop 被 Electron 独占；`headless` 是 profile 名，不是 app 名）。

配套停/起底座（约 15 秒，可逆）：

```bash
cd ~/Documents/AI项目/multi-proxy
bash ./manage.sh stop codex        # 停底座主进程（18790）
dsh headless --patch ~/.dsh/profiles/desktop/cordis.patch.yml "只回两个字：好嘞"
bash ./manage.sh start codex       # 起回来，约 1 秒
```

#### 配套：配置链三件事（读得出「它只会往哪发」，但不就是「发过去了」）

1. patch 文件本身：`~/.dsh/profiles/desktop/cordis.patch.yml:13` = `http://127.0.0.1:18790/v1`，且 YAML 结构完整（7 个 entry，缩进对齐）。
2. **生效时刻**：profile 机制是「app 内置 bundle + `cordis.patch.yml` 覆盖」。`cordis.yml` 只有 4 行是**正常的**（它是空 root，原文件自述「The tree is composed as patches… Edit cordis.patch.yml, not this file」）。判据看**时间戳链**：桌面端进程启动那一刻会重写 `cordis.yml`；只要 patch 的 mtime **早于**桌面端进程启动时间，就说明启动时吃到了新 patch。
3. 进程自证：桌面端主进程命令行显式带 profile 路径（`DeepSeek Harness … ~/.dsh/profiles/desktop …`），`ps aux | grep DeepSeek Harness` 可查。

#### ⚠️ 一个「假阴性」陷阱

`agent-default-model` 若此前被切成 `curator`（挂桥 18795 + 模型 `deepseek-v4-flash`），桌面端会跑到一个**不是我们目标**的 provider 上，且体感变化明显（换模型）。改端点前先确认默认 provider 与模型列表——**换端点不换模型**才不影响日常干活。

#### ⚠️ 第二个陷阱：`apiKeyEnv` 是环境变量，GUI 拿不到

`providers.agnes.apiKeyEnv: AGNES_API_KEY`，但桌面端由 Dock 起进程，外部注入不了。本机实测（2026-10-04）：`agnes-3.0-flash` 这条路由**不带 key 200、带随机 key 也 200**（底座 fail-open），当前不构成阻塞；但若日后出现鉴权报错，**症状出在桌面端而非底座**，排查别走反。

#### 一之二之五、落地后两个日常事实（踩过，2026-10-04 二轮）

##### 事实一：底座是外部进程的，GUI 不带底座

`18790` 由 multi-proxy 的 `manage.sh` 管，**DSH 桌面端不会替你起它**。底座没起时桌面端照样能开、能打字、能选模型——只在**发出请求的那一刻**报 `Connection error.`，还带 5/5 重试，看着像「软件坏了」。

排查顺序先摆清楚：**`curl --noproxy '*' -w "%{http_code}" http://127.0.0.1:18790/health` 先过一次**。HTTP=000 就是底座没起，跟 DSH 没关系。

##### 事实二：改 patch 后 GUI 必须整个退出再开

Electron app 读的是启动那一刻的合成结果，`cordis.patch.yml` 的 mtime 改早了也不热加载。**关窗口不算，要 `Cmd+Q` / Dock 右键 Quit**，重开才生效。

命中「构型层判据过了（dump-config 显示 18790）但 GUI 还是老样子」时，别再怀疑 patch，直接退进程重开。

##### 事实三：`No API key for provider: <name>` 指的是默认 provider，不是模型

2026-10-04 桌面端真实报错二连：

```
● 本轮运行失败 Connection error.
● 本轮运行失败 No API key for provider: curator
```

第二条与端点无关，是 `agent-default-model.provider` 还停在 **`curator`**（2026-10-02 A/B 省钱实验 B 组残留，`baseURL` 指向桥 18795），而该 provider 在 patch 里**没配 `apiKeyEnv`** ⇒ 取不到 key ⇒ 直接报。修法一行，可逆（备份 `cordis.patch.yml.bak-curator-20261004-080900`）：

```yaml
- id: agent-default-model
  config:
    provider: agnes        # 原 curator
    model: agnes-3.0-flash
```

判据：`dsh --profile web --patch ~/.dsh/profiles/desktop/cordis.patch.yml --dump-config | grep -A3 agent-default-model`，确认默认 provider 就是我们在改的那个，**别只盯着 `baseURL`**——两个配置项各管一段，改 baseURL 救不了选错的 provider。

##### 事实四（2026-10-04 二次排障）：同一个 provider 可能在**多处**配置入口，改一个盖不住

`dsh --profile web --dump-default-config` 证实 **bundle 默认树里没有 `agnes`**（DSH 不自带），所以 `agnes` 只能来自：

| 入口 | 原值 | 现状 |
|---|---|---|
| `~/.dsh/profiles/desktop/cordis.patch.yml`（patch 层） | `http://127.0.0.1:18790/v1` | 未动 |
| **`~/.dsh/settings.yaml.imported`（09-17 导入设置快照）** | **`https://apihub.agnes-ai.cn/v1`（直连）** | 已同步为 18790（备份 `settings.yaml.imported.bak-20261004-083500`） |

⇒ **通用规则：改 agent 端点前，先把「同一个 provider 在所有配置入口里的值」全列出来对比，全对齐才算改完。** 只改 patch 会留一个偷偷直连的后门。

##### 事实五：GUI 侧运行时行为**无法自动取证**（试过，别重复踩）

- `screencapture -x` → `could not create image from display`（沙箱拒）；
- `osascript` System Events → **权限违例 `-10004`** ⇒ 没法给 GUI 输入框敲字、没法点按钮；
- 会话日志 `session.v4.jsonl.zstd` **只记 session 头 + 权限预设**（`permission/preset` / `sandbox/mode` / `approval/policy`），不记请求也不记错误——实测维护者 08:29 那条会话只有 4 行 init，说明那次请求**压根没发出去**（他看到的红点多半是历史失败记录）；
- 底座 `codex-proxy.log` 只有启动/config 行，不记请求；18792 面板 `/api/logs` 401、`/api/stats` `/api/metrics` 404、`/metrics` 是 HTML。

⇒ GUI 侧自证走等价链路即可：`dsh headless --patch ~/.dsh/profiles/desktop/cordis.patch.yml "<prompt>"`，底座在 → 正常输出，底座停 → `dsh: TRANSPORT: Connection error.`。

## 二、接一个新 harness 进来的三条硬判据

动手接入时逐条过，**任一条不过就不许放它出网**。

| # | 判据 | 怎么验 | 不过的后果 |
|---|---|---|---|
| ① | **模型端点只配到 multi-proxy**，禁止直连 provider / 复用已登录 session / 内建 endpoint 覆盖 | 看该 harness 的配置与 CLI 参数，端点是否指向本地 18790/18792 | 路由门、省钱、熔断全部对它失效 |

| ③ | **未知 complexity 值必须计数 + 留痕**，不许静默 | `l2/knowledge-base/routing-base.js:182-185`：`mapTier` 是 `m[complexity] || 'medium'`，未知值**静默降级 medium** | 上游传来没见过的值时，路由悄悄跑偏，看不出异常；#8 拍板要的那张"偏移率表"拿不到数据 |

> ⚠️ 判据 ③ 是**待改项**，不是现状。现状是静默降级；改法是把降级改成「计数 + 落一行审计」，改动面很小，但属于改热路径，归 `ITERATION-ROADMAP.md` 排期，不在本文档范围内自动执行。

## 二之二、接入方式优先级（维护者 2026-10-04 拍，跨项目通用）

三条判据回答「**决定了要接，接进来得满足什么**」；这一节回答「**该用哪种方式接**」。顺序不许倒。

| 顺位 | 接入方式 | 什么时候用 | 底座成本 |
|---|---|---|---|
| **1（默认）** | **官方 endpoint 缝**——只改 agent 的 baseURL / base_url / 自定义端点，流量照进底座 | 该 agent 配置里端点可覆盖（DSH 即此类） | **零**：不装插件、不开新 daemon、不碰协议 |
| 2 | **代理网关 / 桥**（如 `tools/token-policy-bridge.js`，`PORT=18795 UPSTREAM=http://127.0.0.1:18790`） | 端点可覆盖但需要在流量上做 rewrite / 策略注入 | 低：一个常驻进程，需 launchd 托管 |
| 2.5 | （补 2026-10-04）**座上桥不座底座**——默认端点填顺位 1，桥只在确认省到钱后再挂 | 顺位 1 已通、且写入侧期望额外省钱 | 见下条限定 |
| 3 | 反代 / 系统级流量劫持 | 端点完全不可覆盖、且 agent 有自身登录态 | 高：触碰协议栈，且常伴随绕过底座的风险 |

**「不支持了再走代理网关」的判定口径**（写判据时直接照抄）：

1. 先查该 agent 的配置项 / CLI 参数 / 官方文档，**搜 `base[-_]?url`、`endpoint`、`apiKeyEnv`、`custom endpoint` 一类**；命中且可填本地地址 → 走顺位 1，**到此为止，不许再往下**。
2. 端点可覆盖但**值必须带它的登录态 / 会话**（例：ccteam 要求先 `claude auth login`，"sitting on `PATH` never counts as logged in"）→ 走顺位 2。
3. 端点不可覆盖，且没有可代理的入口 → 才谈顺位 3；顺位 3 之前先回写本文档，把改不动的地方记下来。

> ⚠️ **2026-10-04 订正：上文原来说「DSH 的 `curator` provider 也是这么配的」不能当同构先例。** `curator` 指 `http://127.0.0.1:18795/v1` 是 `tools/dsh-saving-ab.sh` 的 **A/B 实验 B 组入口**（该脚本 `:6-8` 自述唯一变量是「桥在不在路径上」），且底座此刻整体未启动（launchctl 无条目、18790/18795 不响应）⇒ 它是**未验证的死配置**，不是「已经在用的范本」。codex 指桥的那条是经 launchd 托管的活例，可作先例；**DSH 侧什么都不算数，直到底座先起来。**
>
> Portico 侧同一条规则已进硬规矩⑨（`Portico/AGENTS.md`），跨项目通用。

**新增一条判定口径（补 2026-10-04，接上面三条之后）**：

4. **缝开了 ≠ 接入完成。** 配置里填了本地地址只证明「写对了」，不证明「跑通了」。完成标准三条，缺一不算：底座进程在跑 → 端点 `/health` 或 `/v1/chat/completions` 实测 200 → agent 侧真实发一次请求成功。
5. **默认目标填底座主进程，不填桥。** 桥是按需加载的（维护者 2026-10-02 定调，对内存敏感），把它设为默认会让「桥没起 = agent 废掉」。桥是**座上的增强**，不是**接入的通道**——先无条件过底座，确认省到钱了再谈上桥。
