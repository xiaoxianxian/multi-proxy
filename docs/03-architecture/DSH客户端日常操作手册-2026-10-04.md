# DSH 客户端日常操作手册（接本地底座 18790）

> 面向：要在 DeepSeek Harness（DSH）桌面端里用本地 multi-proxy 底座的人。
> 本文只写「人该怎么操作」，机制细节见 `外部harness接入底座约束-2026-10-03.md`。

## 〇、日常用法：双击 MultiProxy.app（2026-10-04 起不用再敲命令）

日常只需要做**一件事**：在访达里双击 `~/Applications/MultiProxy.app`。它会自己干三件事：

1. 底座（18790）不在跑就拉起来（约 2~4 秒）；
2. 判断 DSH 手上是不是最新配置：不是就重启 DSH，是就不动它；
3. DSH 没开就帮你开起来（Electron 冷启动约 5~20 秒，窗口会显示进度，不用管）。

跑完 DSH 直接选 workspace、打字、回车就行，全程不需要任何命令。

菜单里另有：`⌘D` 开 DSH、`⌘R` 手动重试、`⌘R`(大写) 重载面板、`⌘S` 开机自动启动（**默认是关的**，维护者 2026-10-04 明确否掉底座开机自启，这里同样不擅自开）。

日志在 `~/Library/Logs/MultiProxy-client.log`；底座日志在 `~/Library/Logs/MultiProxy-client/codex-proxy.log`。

> ⚠️ **验证这个客户端时别在 agent 的 shell 里用 `open -a MultiProxy` 试。**
> agent 的 Bash 跑在沙箱里，`open` 起的应用会把沙箱延续到它自己的子进程，
> 结果就是子进程（node/bash）起得来却绑不上端口，现象是「底座死活起不来」——
> **这是测试环境的假象，访达双击（走 LaunchServices，不在沙箱里）不受影响**。
> 复现时直接跑二进制：`nohup ~/Applications/MultiProxy.app/Contents/MacOS/MultiProxy &`。

## 一、先说结论：客户端里怎么发话

**发话这一步没有任何特殊操作，跟普通聊天一样：左边选一个 workspace（本质上就是个文件夹），点进去，底部输入框打字，回车。**

问题从来不在「客户端怎么用」，而在「客户端连哪儿」。所以真正要记住的是下面三条：

### 1. DSH 桌面端不带底座

底座是 multi-proxy 的独立进程（端口 18790），DSH 桌面端**不负责拉起它**。底座没起的时候，GUI 照样能开、能打字、能选会话，只在点发送的那一刻炸出 `dsh: TRANSPORT: Connection error.`。

排障第一动永远是看底座活没活：

```bash
curl -s --noproxy '*' -w "\nHTTP=%{http_code}\n" http://127.0.0.1:18790/health
# HTTP=200 → 底座在跑；HTTP=000 → 底座没起（这是预期行为，不是 DSH 坏了）
```

### 2. 客户端里没有「填端点」的入口

DSH 桌面端有设置面板（包内含 `@deepseek-ai/dsh-client-ui-primitives/lib/settings-form/SettingsForm.module.css`），但按包内自带文档说明，DeepSeek Account 那类编辑器**不提供 API Key 或 Base URL 输入框**。

也就是说：**端点只能改配置文件，改完必须把客户端整个退出再打开（Cmd+Q，不是关窗口）**，Electron 只在启动那一刻读配置，不热加载。

（未证实：GUI 里是否存在全局 Base URL 输入框。本次没有截图权限，无法逐屏确认。）

### 3. 日常最短路径

```bash
# 第 1 步：起底座（每次开机后第一次用就要跑，之后不用）
cd ~/Documents/AI项目/multi-proxy && bash ./manage.sh start codex

# 第 2 步：体检（可选，30 秒，会实发一次真请求）
bash ~/Documents/AI项目/multi-proxy/scripts/dsh-route.sh check
```

体检通过（`自检结果：通过`）之后，开 DSH 桌面端，选 workspace，打字回车即可。

## 二、脚本：一条命令接入 / 还原

`scripts/dsh-route.sh` 把「备份 + 改两处配置 + 起底座 + 自检」压成一条命令。

```bash
bash ~/Documents/AI项目/multi-proxy/scripts/dsh-route.sh on      # 接入 18790（改前各备份一份）
bash ~/Documents/AI项目/multi-proxy/scripts/dsh-route.sh off     # 还原到改动前
bash ~/Documents/AI项目/multi-proxy/scripts/dsh-route.sh check   # 只体检，不动文件
```

它改两处，因为 `agnes` 在机器上是**两份独立拷贝**，只改一份盖不住：

| 入口 | 作用 |
|---|---|
| `~/.dsh/profiles/desktop/cordis.patch.yml` | 主生效源，默认模型也在这（`agent-default-model`） |
| `~/.dsh/settings.yaml.imported` | 9-17 导入的设置快照，同样带一份 agnes |

改法和还原都是**整份备份 / 整份还原**（不是 sed 替换单行），`off` 取最新一份备份恢复。已实测：
- `on` 后 `agnes.baseURL` → `http://127.0.0.1:18790/v1`，`ollama`(11434) / `curator`(18795) 不被波及，patch 里你自己调的 `ui-chat` / `ui-settings-*` 段落原样保留；
- `off` 后与改动前**逐字节一致**（往返验证通过）。

## 三、自己查问题：三道判据

| # | 判据 | 能看到什么 |
|---|---|---|
| 1 | `curl --noproxy '*' .../18790/health` | 底座在不在（HTTP 200 / 000） |
| 2 | `dsh-route.sh check` | 合成配置树里的真正生效 `baseURL`、默认模型，外加一次 CLI 侧真请求 |
| 3 | 断底座证伪：`manage.sh stop codex` → 发一次请求 → `start codex` | 断网时报错、通网时正常＝链路真的接在底座上 |

### 会话日志能自证（比上面都准）

DSH 会把每次请求的决策记在 zstd 压缩的 session 日志里，解出来能直接看到走了哪个 provider / model、成功还是失败：

```bash
# 找到最新的会话日志，然后
zstd -dc <那个 session.v4.jsonl.zstd | python3 -c "
import sys, json
for l in sys.stdin:
    d = json.loads(l) if l.strip().startswith('{') else {}
    t = d.get('type')
    if t in ('request/header','request/context','assistant/attempt'):
        print(t, '|', json.dumps(d, ensure_ascii=False)[:200])
"
```

历史实例（两条相邻会话，结果相反）：

- `test 1` 的 `session-7df0e497`（08:28）：`request/header` 是 `agnes / agnes-3.0-flash`，随后 5 次 `llm/retry` 全是 `{"message":"Connection error.","code":"TRANSPORT"}` → 失败。
- `test 2` 的 `session-c0cb5718`：`provider: agnes / model: agnes-2.5-flash`，`turn/end` 的 `reason.kind = completed` → 成功。

**教训**：日志里 `finish.reason.kind=error` 就是这次请求真失败了，别再靠猜。另外别只盯着最新那个 session 文件就下结论——那次我先解了同一目录里另一个 405 字节的空壳会话（只有 session 头 + 权限预设），差点误判成「压根没发出去」。

## 四、能不能推广给别人：我的判断

**按今天这个形态，不够格推广。** 理由摆在这里：

1. 需要先起一个外部底座进程（否则客户端直接 TRANSPORT 报错，新手完全不知道去哪看）；
2. 端点改在**两个 YAML** 里，不是一处；
3. 改完必须 Cmd+Q 整个重开客户端，跟「关窗口再开」不一样——这中间任何一步漏了都会得出「改了没用」的错误结论；
4. ~~模型名还有坑：不同 workspace 实际跑的模型会不一样（今天实测到 `agnes-2.5-flash` 成功、`agnes-3.0-flash` 失败）~~ —— **这条归因错了，2026-10-04 下午订正**：两条会话连的是同一个 `agnes` provider，区别只在 `model` 字段（`agnes-3.0-flash` / `agnes-2.5-flash`），而失败日志是 **5 次 `llm/retry` 全是 `TRANSPORT / Connection error.`**——这是**连不上**，不是模型不支持。底座侧直接 POST `agnes-3.0-flash` 返回 200，模型本身没问题（见 §三判据 2）。真要留一条教训的话是：**看到 `Connection error.` 就只查底座活没活，别去怀疑模型名**。`baseURL` 和默认模型各管一段这条仍然成立（它是 08:09 那次 `No API key for provider: curator` 的根，跟端点无关）。

能推广的最小形态就是把这个脚本交出去：`on` 一条接入、`off` 一条还原、`check` 一条体检，别人不需要知道有几份 YAML。

再往上做推广，还缺两件东西：
- GUI 里能**看见**当前走哪个端点（现在只能敲命令看）；
- 底座没起时给一句人话提示，而不是 `Connection error.` 让新手干瞪眼。
