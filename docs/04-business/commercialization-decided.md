## 二、20 题决策（含推导依据）

### 一、市场判断
| # | 决策 | 依据 |
|---|------|------|
| 1.1 目标市场 | **开发者自部署 + 企业内部私有化** | 全本地 Harness（4 proxy + L2 在跑）天然贴合；个人开发者首站，企业私有化延伸 |
| 1.2 直接竞品 | OpenAI Harness（托管）/ AutoGPT·LangGraph·CrewAI（编排框架）/ cc-switch（15721 多代理切换） | 现状锚点；差异点＝**全本地 + 自动选性价比** |
| 1.3 差异化 | **全本地（隐私/可控）+ M6 自动选性价比 + 本地 judge** | 比 OpenAI 托管更彻底；单一能力壁垒弱，胜在「全本地组合」 |
| 1.4 时机窗口 | **本地大模型（Qwen3.8-27B/MLX）已能扛 judge/decompose 的临界点** | 本地执行者成熟度够，是「全本地」卖点成立的前提 |
| 1.5 市场够大吗 | 【**待补真实信号**】技术视角推断「AI 开发者运维 agent」是刚需，但**未访谈不下结论** | 现状锚点已标「纯技术视角推断」；建议先用开源 + DSH 验证需求 |

### 二、客户与场景
| # | 决策 | 依据 |
|---|------|------|
| 2.1 谁付费 | **个人开发者（首站）→ 中小团队 → 企业私有化** | Q2 已拍；3 proxy（codex/hermes/cursor）+ 智能路由＝运维台形态 |
| 2.2 核心付费场景 | **多 agent 混用时自动选性价比（M6 cost-optimization）** | 差异化最强场景；coding/writing/vision/cheap 任务级派发 |
| 2.3 付费意愿 | 【**待补真实信号**】「能算花费」≠「愿为算付费」 | 现状锚点；先用开源攒信任，增值层（配额/团队/SLA）验证意愿 |
| 2.4 获客 | **开源 + DSH 生态（唯一潜在分发口，等 0.2）+ 桌面壳安装体验** | 当前无付费渠道，首站靠口碑 + 开源 + 生态 |

### 三、产品与交付形态
| # | 决策 | 依据 |
|---|------|------|
| 3.1 开/闭源 | **内核开源 + 增值（团队/配额/SLA/云端编排）闭源/付费** | 契合非侵入设计（不写 agent 文件/门控默认关），开源成本低利于生态 |
| 3.2 交付形态 | **MVP＝桌面壳（Electron）+ 智能路由 + 成本面板；后续 SaaS 自部署** | 老板明确提过「纯网页不够，要桌面壳整装/卸」；P5 优先级提升 |
| 3.3 功能边界 | **一期＝M6 智能路由 + 成本面板 + 桌面壳；二期＝告警/记忆/团队** | 已落地能力 vs 未做能力对照（见现状锚点 3.3） |
| 3.4 MVP 范围 | **智能路由 + 成本面板 + 桌面壳** | Q4 已拍 |

### 四、商业模式与定价
| # | 决策 | 依据 |
|---|------|------|
| 4.1 收费方式 | **开源 + 增值（用量 / 配额 / 团队订阅）** | 本地模型成本≈0；`cost.js` 已能算 token×单价 + 余额趋势 |
| 4.2 单价 | **按成本梯度分档：本地免费 → Agnes 免费 → DeepSeek 缓存红利 → Qwen 默认；增值层按任务量/团队席位** | 四层 fallback 自带成本梯度（见 `m6-action-checklist.md` 价基线） |
| 4.3 免费层 | **DSH 生态 + 本地全跑（免费层天然成立）；增值＝云端编排/配额/团队/SLA** | DSH DS1 已落；免费层无成本 |
| 4.4 变现最短路径 | **开源 + 云增值** | Q3 已拍；先开源攒用户 → 云端/团队变现 |

### 五、风险与壁垒
| # | 决策 | 依据 |
|---|------|------|
| 5.1 技术壁垒 | **单一能力弱（`findProviderByType` 是工程细节），壁垒靠「全本地 + 生态 + 数据 + 切换成本」组合** | 全本地 + 本地 judge 是大模型成熟后自然结果，易被复制 |
| 5.2 护城河 | **① DSH 生态（分发）② 成本/审计数据（积累）③ 切换成本（桌面壳 + 编排绑定）** | 风险：样本要时间、DSH 受制于外部版本 |
| 5.3 最大风险 | **本地 Qwen 扛不住 judge/复杂任务 → 全本地卖点塌**（需在 MVP 前用真实 judge 任务压测验证） | 旧 D5 路由塌缩风险**已消除**（4 provider 全 enabled + 真名对齐 + E2E 实证 coding→deepseek HTTP 200） |

## 四、仍需老板补的真实信号（不臆造）

> 以下 4 项我无法用代码/文档定，需要老板给真实信息，否则只能停在「推断」。
> **（2026-09-18 贾维斯补充初步判断：便于老板拿去和外部评估对齐；均为「待老板真实信号定稿」，非结论、非臆造。）**

1. **1.5 / 2.3 · 市场大小 & 付费意愿**
   - **需老板补**：做过哪些客户访谈 / 反馈？哪怕 5 个潜在用户的口述。
   - **我的初步判断（待老板信号定稿）**：首站=个人开发者（与现有 4-proxy「运维台」形态零迁移）；暂不抢企业私有化（壁垒弱、获客贵）。付费意愿上「本地模型成本≈0，能算花费≠愿为算付费」——先用开源 + DSH 攒信任，增值层（配额/团队/SLA）在 MVP 验证后定价；**不下"市场够大"的结论，需至少 5 个用户口述支撑**。
2. **P5 桌面壳**
   - **需老板定**：是否启动 + 大致工时预期。
   - **我的初步判断**：建议启动（老板既定诉求「纯网页不够，要桌面壳整装/卸」）。核心差异化=Electron 壳 + 自动检测 agent base_url 占用（如 cc-switch:15721 等占用则报错不开启），估 1 周可出 MVP 壳。阻塞点=老板定"何时启动"。
3. **DSH 生态**
   - **需老板补**：能否拿到 DSH 0.2 时间线 / 收录流程。
   - **我的初步判断**：DS1 已落（2 个 SKILL.md），DS2/DS3 暂缓是**有意为之**（DSH 0.2 未稳定 + #1496 guardrail 未修，见 `bundle-design.md §5`），非遗漏。这是当前唯一潜在分发口，拿到时间线即可定 2.4 获客。
4. **5.3 · 最大风险（本地 Qwen 扛不住 judge / 复杂任务）**
   - 旧 D5 路由塌缩风险**已消除**（4 provider 全 enabled + 模型真名对齐 + coding→deepseek E2E HTTP 200，见 §5.3）。
   - **需老板定**：是否在 MVP 前做 1 个真实 judge 任务压测，验证全本地卖点是否成立。
   - **我的初步判断**：风险真实但可缓解。建议 MVP 前压测 1 个 judge 任务（Qwen3.8-27B/MLX）；若扛不住则走「judge 走远端、执行本地」的混合方案，不影响全本地主卖点。
