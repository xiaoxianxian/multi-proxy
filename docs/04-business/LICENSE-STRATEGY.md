# 开源协议策略（防摘桃硬武器）

> 目的：在"开源推广清晰"与"防大厂商用白嫖"两个目的之间，用**协议**而非保密做护城河。
> 受众：作者决策 + hermes。本文件为**决策文档，不生成 LICENSE 文件**，待作者拍板协议后再由 hermes / 作者落地。
> 作者：搭档 · 2026-09-26

## 1. 场景与矛盾

- 一个人维护，无团队、无法务。
- 目的①：开源、推广清晰，让人人知道定位、能提完善建议。
- 目的②：防大厂 / 大团队在雏形期意识到价值，白嫖思路 + 代码快速迭代成他们的产品。
- 矛盾：推广要公开详细，防摘桃要模糊晚公开。
- **解法不是保密，是用协议把合规成本堆高。**

## 2. 残酷事实

- **思路 / 抽象方案不受任何知识产权保护**，大厂抄你的"想法"你挡不住；法律只保护具体代码实现。
- 技术保密对大厂几乎无效（逆向 + 重写比你快）。
- 因此：思路层防御靠"先发卡位 + 社区心智"；代码层防御靠"协议硬约束"。

## 3. 协议对比

| 协议 | 防商用白嫖 | 推广友好 | 结论 |
|------|-----------|---------|------|
| MIT / Apache-2.0 / BSD | ❌ 等于开门，随便闭源商用 | ✅ 最友好 | 直接排除 |
| MPL-2.0（文件级 copyleft） | ⚠️ 改的文件须开源，但可闭源整合 | ✅ | 偏弱 |
| **AGPL-3.0** | ✅ 强 copyleft，连 SaaS / 网络部署都须开源衍生 | ✅ 开源即推广 | **推荐主力** |
| SSPL | ✅ 服务端必须开源，云厂商劝退 | ⚠️ 部分社区抵触 | 备选 |
| CC-BY-NC / 自定义非商用 | ✅ 直接禁止商用 | ⚠️ 限制商用贡献 | 可选补充 |

## 4. 推荐方案

**主推：AGPL-3.0。**

- 任何人可免费使用、修改、再分发，但若提供网络服务（SaaS）或分发衍生，必须同样以 AGPL 开源全部修改。
- 大厂想把你做成闭源产品白嫖 → 合规成本极高（必须开源他们的版本），实质劝退。
- 不影响"推广清晰"：AGPL 项目开源即天然推广，社区可自由使用提建议。

**升级选项：AGPL-3.0 + 商业授权（双许可）。**

- 在 AGPL 之外，声明"商业用途需向作者获取单独授权（可付费）"。
- 既开源推广、又保留未来商用收费权（Redis / MongoDB / Elastic 经典打法）。
- 适合"想让人用、又想未来能变现"的诉求。

## 5. LICENSE 写法（待拍板后落地）

### 5.1 AGPL-3.0 标准做法

- 仓库根放 `LICENSE` 文件，内容为 AGPL-3.0 官方全文（https://www.gnu.org/licenses/agpl-3.0.txt）。
- 每个源文件头部加版权声明：
  `Copyright (C) 2026 <作者/Jason> — multi-proxy. Licensed under AGPL-3.0.`
- 根目录 `README.md` 顶部加许可章节，明确 AGPL-3.0 及（若采用）商业授权说明。

### 5.2 双许可商业授权声明模板（可选）

```
本项目的开源版本以 GNU AGPL-3.0 许可。
如需将本项目用于闭源商业产品、或提供未开源的商业 SaaS 服务，
请与作者联系获取单独的商业授权：<联系方式>。
```

## 6. 依赖许可合规（hermes 推进时注意）

- 项目现有依赖：Express / Flask / SQLite / better-sqlite3 等，均为宽松许可（MIT / BSD），AGPL 项目引用它们无需修改，但须保留其版权声明、不破坏其许可。
- **禁止在 v1 收口期引入 GPL-2.0 等与 AGPL 不兼容的依赖**，避免传染性冲突。
- 引入任何新依赖前，先查其 license 字段，确认与 AGPL-3.0 兼容。

## 7. 护城河优先级（重申）

**协议硬约束 > 社区先占心智 > 你的迭代速度 > 技术保密（最后，几乎没用）。**

## 8. 给 hermes 的指令

- 本文件为决策文档，**当前不生成 LICENSE 文件、不修改任何项目代码**。
- 待作者在对话中拍板"采用 AGPL-3.0 / 或双许可"后，再由 hermes 或作者在根目录生成 LICENSE + 补源文件头 + 更新 README 许可章节。
- 推进时注意第 6 节依赖合规，勿引入不兼容许可。
