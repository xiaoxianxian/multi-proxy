## 二、问题清单

### A. 安全

**A1（严重）cursor 代理 admin API 完全无认证**
- `cursor/src/server/app.ts:8-24`：helmet/cors/json 中间件齐全，但 `/admin-api` 路由没有任何 auth 中间件；`cors()` 无参调用即 `Access-Control-Allow-Origin: *`；`start.ts:5` 监听默认绑 `0.0.0.0`。局域网内任意主机可增删供应商、改路由设置、读日志。与 codex/hermes 的 `PROXY_AUTH_TOKEN` 机制严重不一致。

**A2（高）PROXY_AUTH_TOKEN 未设时认证静默失效**
- `codex-proxy/proxy.js:21`、`hermes-proxy/proxy.py:47`：`if (!AUTH_TOKEN) return next()`。CLAUDE.md 称"可选"，但这是 fail-open 设计——忘记配环境变量等于裸奔，且 codex-proxy 同样监听全部接口（proxy.js:527 未指定 host）。建议至少默认绑定 127.0.0.1 并在未设 token 时打显眼告警。

**A3（高）CSP 自我削弱**
- `server.js:172-174`：`script-src 'self' 'unsafe-inline' cdn.jsdelivr.net unpkg.com`。前端 4 个 HTML 全是内联 JS/CSS，`unsafe-inline` 使 CSP 对 XSS 基本无效；再放行两个公共 CDN（可被用于加载任意脚本，若 CDN 被污染则直接 RCE 级风险）。既然页面无框架依赖，应内联 hash 或 nonce 收紧。

**A4（中）token 比较非常量时间 + 错误信息不区分**
- `codex-proxy/proxy.js:23`、`hermes-proxy/proxy.py:49` 用 `===` 比较 token，存在时序侧信道，应用 `crypto.timingSafeEqual` / `hmac.compare_digest`。
- `server.js:129-131`：任何 JWT 校验失败都返回 `'Token expired'`，语义误导（伪造 token 也报过期）。

**A5（中）SSRF 面**
- `server.js:1092-1139`（test-connection）、`server.js:1172-1226`（fetch-models）：baseUrl 完全由客户端提供，服务端代为发起请求，可探测内网（含云 metadata 地址）。虽在 requireAuth 之后，但结合 A1 的 cursor 无认证生态和单用户密码模型，仍建议加 URL 协议/host 白名单或私网段黑名单。
- `server.js:1110`、`1194` 把 API key 放 URL query（Gemini 惯例所致），会落入各级访问日志。

**A6（中）错误信息泄漏不一致**
- `codex-proxy/proxy.js:264、319、342、522` 直接把 `e.message` 回给客户端；`cursor/chatHandler.ts:213` `Proxy error: ${e.message}` 同样外泄内部细节。与 forwardProxy/chatHandler 上游脱敏的严谨风格自相矛盾。

**A7（低）MANAGER_PASSWORD 明文比较**
- `server.js:107-108`：环境变量路径走 `input === envPassword` 明文比较，完全绕开 bcrypt（代码有 WARNING 但仍允许）。另 `server.js:998-1007` 首次 setup 模式无任何鉴权，先到者可抢占设密——本机多用户环境下是竞态窗口。

**A8（低）spawn 泄漏父进程全部环境变量**
- `server.js:519`：`env: { ...process.env }` 把 JWT_SECRET、MANAGER_PASSWORD、PROXY_AUTH_TOKEN 全部传给子代理进程，子进程及其再衍生的工具都能读到管理器凭据。应只传必要变量。

**A9（低）cursor 掩码掩的是密文**
- `adminRoutes.ts:29`：`p.api_key.slice(0, 4) + '****'` 截的是 AES-GCM 密文前 4 hex 字符，掩码无意义且泄露密文前缀。应先解密再掩码，或干脆只返回 `(encrypted)` 标记。

### B. Bug（确定性缺陷）

**B1（高）启动失败的进程永远不会被杀**
- `server.js:767-768`：
  ```js
  delete proxyProcesses[name];
  if (proxyProcesses[name]) proxyProcesses[name].kill('SIGKILL');
  ```
  先 delete 再判断，恒为 false——死代码。`server.js:694-695` 一模一样的错误又出现一次。意图是端口未绑定时 SIGKILL 清理半死进程，实际从未执行，僵尸进程会残留占位。

**B2（高）停止代理期间自动重启会"复活"刚被停掉的进程**
- `server.js:563-564`：close handler 里 `await waitForPortFree(...); restartProxy(name, backoff)` 是一个悬空的延迟任务，没有句柄可取消。用户在退避窗口内调用 `POST /api/stop/:name` 时，stopProxy 重置了 recovery 计数（server.js:655-656），但定时重启照样触发，而 `restartProxy` 的守卫只剩 `consecutiveFailures >= 5`（server.js:683）——已被清零，于是进程被拉起。需要引入 generation/token 取消机制。

**B3（高）并发 start 缺少互斥，可双开进程**
- `server.js:738-759`：两次快速点击 start，两个请求都在对方 spawn 前通过 `isProcessRunning` 检查（此时 lsof 尚未探测到新端口），双双 spawn；第二个进程端口冲突退出，非零 exit 又触发崩溃恢复链路空转。`restartProxy:674-675` 有 existing 守卫，但手动 start 路由没有等价的 in-flight 锁。

**B4（高）fetchProxyApi 不带 x-proxy-auth，token 启用后健康检查必挂**
- `server.js:437-455` 不添加认证头，而 `codex-proxy:229` 和 `hermes-proxy:280` 的 `/health` 都挂在 `requireAuth` 后面。一旦设置了 `PROXY_AUTH_TOKEN`，`/api/status` 的 health 探测（server.js:713）永远收到 401。forwardProxy 补了头（server.js:914-918），fetchProxyApi 漏了。

**B5（中）stopProxy 子进程收集算法错误**
- `server.js:612-625`：`pending = children.slice(children.length - pending.length)` 假设"新增子进程数 == 上一轮 pending 长度"，完全不成立（ps 输出行数是本轮所有子进程数）。结果：孙子进程大概率遍历不到，PID 白名单漏掉真正的监听进程时 stop 失败。应改为 `pending = newChildren`（每轮 diff 出的新集合）。

**B6（中）codex-proxy 流式响应疑似根本跑不通**
- `codex-proxy/proxy.js:509`：`response.body.pipeTo(res)`——`response.body` 是 WHATWG ReadableStream，`pipeTo` 要求 WHATWG WritableStream，而 Express 的 `res` 是 Node ServerResponse，二者不兼容，运行时会抛 TypeError 被 catch 成 504。应改用 `Readable.fromWeb(response.body).pipe(res)`。对比 cursor 的实现（chatHandler.ts:145-167 手动 reader 循环）是正确的。

**B7（中）AbortSignal.timeout 会掐断长流式响应**
- `codex-proxy/proxy.js:493`、`cursor/chatHandler.ts:129`：120s 定时器从请求发起就开始计时且对流式传输全程有效，超过 2 分钟的长生成会在中途被 abort。流式场景应在收到响应头后清除 signal/改用 idle timeout。

**B8（中）updateConfigToml 静默假成功**
- `codex-proxy/proxy.js:92`：正则 replace 匹配不到 `model = "..."` 行时不报错，函数返回 `success: true`（102 行），用户以为切换成功实则配置未变。应检查替换是否发生。

**B9（低）cookie 分支永不可达**
- `server.js:121` 读 `req.cookies.auth_token`，但 package.json 无 cookie-parser 依赖也未 `app.use(cookieParser())`，`req.cookies` 恒为 undefined。要么补依赖，要么删分支。

**B10（低）hermes-proxy 没有 /v1/chat/completions**
- `proxy.py:279-620` 全部路由清单里无 chat completions，但 manager 白名单（server.js:1042）放行了该端点，转发过去必然 404。另外 `proxy.py:19` 导入的 `stream_with_context` 从未使用——疑似流式功能被删了一半。

**B11（低）cursor DELETE models 不校验存在性**
- `adminRoutes.ts:117-121` 恒返 `success: true`，与同文件 providers 的 404 行为不一致；`POST /admin-api/routes`（86-93 行）对 id/default_model 零校验，undefined 直接进 SQLite 绑定报错。

### C. 性能 / 资源

**C1（高）appendLog 每写一条日志全量读写整个文件**
- `server.js:210-214`：每次 append 都 `readFileSync` 整个 requests.log 再 `writeFileSync` 截断到 5000 行。5000 行 × 每次 forward 两条日志（923、931 行），O(n²) I/O 且同步阻塞事件循环；并发请求还会交错读写导致丢行/截断竞争。应改为内存计数 + 定期轮转，或至少异步化。

**C2（中）forwardProxy 无法处理流式响应**
- `server.js:906-907`：axios `timeout: 15000` + 自动缓冲完整响应体。经 manager 转发的 `/v1/chat/completions`：LLM 生成普遍 >15s 必超时；SSE 也被整体缓冲后 `res.json(response.data)`（932 行）一次性吐出，破坏流式语义。这是统一入口路径上的硬伤。

**C3（中）cursor round-robin 每个请求写一次数据库**
- `chatHandler.ts:21-27`：rr_index 持久化意味着每次聊天请求一次 SQLite 写（含 fsync），高并发下纯开销。索引存内存即可，丢失一次轮询位置无关紧要。

**C4（低）RateLimiter 与 isReadOnlyEndpoint 是死代码**
- `cursor/rateLimiter.ts` 实现了完整令牌桶却从未在任何路由挂载——cursor 代理实际零速率限制；`server.js:134-138` isReadOnlyEndpoint 同样无人调用。

**C5（低）console.log 覆盖破坏对象输出**
- `codex-proxy/proxy.js:10-13`：`args.join(' ')` 使对象变成 `[object Object]`，排障信息丢失，应用 `util.format`。

### D. API 设计一致性

**D1** 三套代理错误格式三种风格：codex `{success, error, code}`、cursor 混用 `{error: {message}}`（app 层 middleware.ts:20）与 `{success, error, code}`（handlers）、hermes 在 `test_connection` 里有时返回 HTTP 200 + success:false（proxy.py:471、473）有时 400（461）。manager 前端被迫做双格式兼容。
**D2** ID 生成不一致：codex `Date.now(36)+random`（proxy.js:213）vs hermes 时间戳+random（proxy.py:84）vs cursor UUID——虽然 P1 号称已统一。
**D3** hermes `get_balances` 返回字符串混合类型（'未启用'/数字/'查询失败...'，proxy.py:593-618），manager 侧还要再做一次 parseFloat 规整（server.js:1246-1255），契约脆弱。
**D4** `hermes-proxy` 的 `find_provider` 第 4 级兜底按前缀匹配 provider 名（proxy.py:247-256），`codex-proxy` 按子串匹配（proxy.js:181-184）：模型名包含关键词即路由，可能静默错路（如自建模型名含 "openai"）。

### E. 进程管理补充

**E1** `waitForPortBound` 只检测"端口被任何人占用"（server.js:417-435），不能证明是新起的子进程绑定的——若端口恰被别的应用占用会误报启动成功。
**E2** fault 态（连续 5 次崩溃）只能靠手动 start 重置（server.js:742），UI 之外没有任何自动恢复/告警升级路径，持久化文件损坏时 `loadCrashRecoveryState` 静默返回 `{}`（server.js:286-289）尚可接受，但 fault 判定依赖文件与内存双份状态，`saveCrashRecoveryState` 失败仅打日志，可能出现计数漂移。
**E3** `isProcessRunning` 的 lsof 回退（server.js:366-372）无法区分"我们的代理"与"任意占用该端口的进程"——已知限制（CLAUDE.md 有记载），但配合 B2/E1 会放大误判。
