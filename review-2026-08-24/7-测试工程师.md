# proxy-rebuild 测试代码字段级评审报告

评审范围：实际通读了全部 21 个测试文件（约 5,460 行），并与生产代码（server.js 1413 行、codex-proxy/proxy.js、hermes-proxy/proxy.py、cursor src/ 共 1601 行）交叉核对。以下按维度给出结论，每条附证据。

---

## 一、总体结论

**这套测试的核心问题是“测试副本而非测试本体”**。大量测试文件把生产函数复制进测试文件里再测，绿灯无法证明生产代码正确。其次是前端“字符串包含”式伪测试占比过高。cursor 的 engine-monitoring 和 hermes 的 Flask test client 部分是明显亮点。

---

## 二、做得好的地方

1. **hermes-proxy/tests/test_http_endpoints.py** 是全仓最规范的：真实导入 `proxy` 模块、用 monkeypatch 隔离 HOME/CONFIG_YAML_PATH（L66-78）、autouse fixture 每类重置状态（L65-79）、Flask test client 打真路由（L80-106）。这才是集成测试该有的样子。
2. **cursor-multi-model-proxy/tests/unit/engine-monitoring.test.ts** 质量最高：真实 import 生产类（L1-3）、覆盖三态熔断转换（OPEN→HALF_OPEN→CLOSED，L116-157）、令牌桶边界（恰好 60 个，L203-210；容量封顶 L212-226）、用手动 `Date.now` 替换模拟时间推进避免 sleep（L122-127）。
3. **database.test.ts 的外键/级联语义覆盖完整**：FK 禁止孤儿插入（L275-283）、级联删除（L285-306）、FK 关闭时孤儿清理（L322-357）——概念上很到位。
4. **rate-limit.test.js 验证了标准头和中间件顺序**：`ratelimit-policy` header（L120-128）、lockoutLimiter 先于 authLimiter 的链序行为（L131-180）。
5. **multi-proxy-manager 有真正的 Playwright E2E 层**（tests/e2e/，6 个文件 902 行），含安全组（CSP/X-Frame-Options 头断言，06-security.test.ts:19-54），四个子项目里唯一有 E2E 的。
6. **安全测试 payload 广度不错**：单编码/双编码路径穿越（security.test.js:88-92）、`:id` 参数字符白名单（L76-86）、esc() 对 script/svg/iframe/javascript: URI 的逐项断言（L110-158）。

## 三、严重问题（伪测试 / 测的是副本）

### P0-1 大面积“复制实现到测试里”，测试通过≠生产代码正确

- **codex-proxy/tests/proxy.test.js**：文件头注释自曝 "Extract pure logic from proxy.js for testing"（L1），但 `findProvider`（L29-38）、`parseConfigToml`（L40-67）、`updateConfigToml`（L69-87）全部是在测试文件内重新定义的副本，没有一行 `require('../proxy')`。proxy.js 改了逻辑这些测试照样绿。
- **codex-proxy/tests/integration.test.js 更严重**：它不是测 proxy.js，而是 `beforeAll` 里**手工搭了一个镜像 Express app**（L48-134），路由行为是测试者自己写的。所谓“集成测试”测的是一个平行实现。且两份 `UPSTREAM_MODELS` 已经漂移——proxy.test.js:19 与 integration.test.js:22 的 Kimi 模型列表内容不一致，正是复制策略腐化的实证。
- **crash-recovery.test.js**：`appendLog` 在 beforeEach 里整段重写（L21-40，注释"matches server.js implementation"）；崩溃恢复状态机是本地函数+手工赋值模拟（L146-256）——L172-183 “优雅退出重置计数”只是给局部对象赋 0 再断言是 0；L220-225 backoff 公式是把生产公式抄过来代入数字。**server.js 真实的 restart 逻辑零覆盖**。
- **security.test.js DoS 部分**：`checkPasswordSize` 是照抄 server.js:740 逻辑的本地复制品（L198-204），并没有向 `/api/auth/login` 发超大密码验证 413。
- **multi-proxy-manager/tests/unit/providers.test.js 全文 125 行没有任何 import**：每个用例构造一个字面量对象再断言它的字段（如 L19-26 构造 transformed 再查 max_tokens；L117-123 先造 `{id:'gpt-4',...}` 再断言 `model.id` 存在）。这是恒真测试，删掉整个文件信息量为零。

### P0-2 cursor 的 database.test.ts 测试的是测试自己的 schema

createTestDb()（database.test.ts:17-75）在测试里手写了一遍建表 SQL，而不是调用 `src/db/database.ts` 的初始化。若 database.ts 加列、改约束、改索引，这 443 行测试依然全绿。**src/db/database.ts 实际覆盖率接近 0**。

### P0-3 前端测试是“源码字符串包含”检查

dashboard/login/logs/proxy-config/design-system 五个文件共约 260 个用例几乎全是 `expect(html).toContain('function switchTab')` 式断言：

- proxy-config.test.js:89-105（断言 HTML 里出现 `switchTab`、`classList.add('active')` 字样）
- logs.test.js:119-137（断言出现 `window.applyFilters`、`l.level ===` 字样）
- login.test.js:115-142（密码强度计算只断言源码里有 `>= 12`、`Math.min(score, 4)` 字符串）
- design-system.test.js 整个 443 行是对 CSS 文件做 `toContain('--color-primary')`

这类测试不执行任何 JS，改名/重构即碎、逻辑错了照绿。CLAUDE.md 里“现有 206 个测试已充分”的判断（P1-2 暂缓项）过于乐观——其中大量是这类低价值用例。唯一的例外是 dashboard.test.js:161-173 用正则抽取 `var action = ...` 表达式并校验只允许 start/stop，这是本组唯一有 teeth 的用例，但正则方式极脆。

## 四、明确的 Bug / 缺陷

1. **process-management.test.js:42-52 端口检测 fallback 是死代码**：`isPortInUseViaLsof` 的 net.Socket 分支发起异步 connect 后立即 `return false`（L48），connect 回调永远不会改变返回值——该 fallback **恒返回 false**。如果 lsof 缺失，这个测试辅助函数完全失效且静默。
2. **process-management.test.js:185-191 存在竞态导致断言可能永不执行**：spawn 一个立刻退出的进程后，在 `proc.on('close', ...)` 回调里才注册断言；若进程在监听器挂上前已退出（`node -e 'process.exit(0)'` 完全可能），回调永不触发，用例“通过”但什么都没验。
3. **security.test.js:160-193 结构损坏**：两个 `it`（iframe 注入、data: URI）游离在任何 describe 之外，且与 L162-175 内容**逐字重复出现两次**，中间夹着重复的 "DoS via oversized payloads (T12)" 注释头（L177 与 L195）。典型的合并事故残留；顶层 it 能跑但说明无人审查过这份文件的输出。
4. **engine-monitoring.test.ts 手动替换 `Date.now` 无 try/finally 保护**（L122-127、L136-142、L197-200、L219-225）：任何中间 expect 失败都会把被劫持的 `Date.now` 泄漏给同进程后续测试，产生跨用例污染的幻影失败。
5. **integration.test.js:241-250 用例打真网络**：POST /v1/chat/completions 会真实 `fetch('https://api.deepseek.com/...')`（L116），仅靠 `expect(status).not.toBe(400)` 兜底，15s 超时下离线环境必挂或慢，且断言弱到几乎不可失败。
6. **api.test.js:27-30 条件断言可静默跳过**：`if (res.body.codex) {...}`——当 /api/status 因环境异常不含 codex 时用例照样通过，掩盖回归。同类问题：L85-96 当 MANAGER_PASSWORD 未设直接 return（无条件 skip 却不计为 skipped）。
7. **e2e/06-security.test.ts:56-87 的 XSS 用例没有注入任何恶意数据**：它登录后只是确认 `#providersBody` 可见、页面无外部 script 标签（L82-86）。供应商名含 `<script>` 的核心场景根本没构造，标题与实际验证内容不符，给出虚假安全感。另全文件大量 `waitForTimeout(1500)`（L62、L74、L95）是 Playwright 反模式。
8. **crash-recovery.test.js:81-99 暴露的生产实现性能缺陷被测试固化**：appendLog 每写一行就全文件读回+重写以截断 5000 行（对应实现 L34-36），O(n²)；5100 行循环用例跑得动但暗示生产日志写入在大文件时会拖慢请求路径。

## 五、Mock 策略评价

本仓库的问题不是 mock 过度而是**反向极端——不用 mock，改用复制**。后果：

- 白名单匹配器 `isAllowedEndpoint` 在 security.test.js:30-60 和 crash-recovery.test.js:349-367 各抄了一份，**且两份的 `:id` 校验逻辑不同**（前者有 UUID/数字/字母数字白名单 L44-49，后者 `if startsWith(':') continue` 直接放行 L361）。三个版本（含 server.js 本体）可以各自漂移互不知晓。
- esc() 测的是 tests/unit/helpers/esc.js 这个测试自有副本，与四个 HTML 页面里各自内联的 esc 实现无绑定。
- 合理的 mock 只出现在 engine-monitoring（Date.now）和 hermes（monkeypatch 全局路径），这两处做法值得推广：**mock 外部依赖（时间/文件系统/网络），import 真实被测物**。

## 六、缺失的测试场景

1. **代理认证链路零覆盖（高优）**：hermes-proxy/proxy.py 的 `require_auth` 装饰器保护了全部 16 个写端点（proxy.py:280-588），但 tests/ 目录 grep `PROXY_AUTH_TOKEN` 为 0；manager 的 `x-proxy-auth` 头注入（server.js:917）同样无任何测试引用。P0 修复记录里的核心安全机制处于无保护状态。
2. **流式（SSE）路径全仓零测试**：cursor 的 streamTranslators.ts、streamHandler.ts 无任何测试引用；各 provider 的 denormalizeResponse 只测了 `stream:true` 直接透传（providers.test.ts:89-93 等），Anthropic/Gemini 的 SSE 分块翻译——代理类服务最容易出 bug 的地方——完全没有用例。
3. **cursor 的 SecretsManager（crypto.ts:58-89）加解密、密钥文件生成、错误密文处理零测试**。AES-GCM 的 tag 校验失败路径、IV/tag 切片边界都未验证。
4. **JWT 安全负路径**：manager 用 JWT 鉴权（api.test.js:7 自签 token），但没有过期 token、篡改签名、错误 secret 的用例。
5. **并发场景为零**：多代理同时启停、killPort 两阶段信号（SIGTERM→SIGKILL）、SQLite WAL 并发写、round-robin 并发下的索引竞争，均无用例。
6. **性能测试为零**：日志轮转 O(n²)、50mb body limit（integration.test.js:50）下的内存行为等均未量化。
7. **金字塔比例失衡**：E2E 仅 manager 有（且依赖 18792 真实服务存活）；codex-proxy/hermes-proxy/cursor 三个子项目没有任何端到端验证，cursor 甚至没有对 src/server/app.ts 任一路由的 supertest。

## 七、可维护性建议（按 ROI 排序）

1. **消灭副本**：codex-proxy 抽出 `lib/routing.js` 供 proxy.js 与测试共用；manager 把 `isAllowedEndpoint`/`FORWARD_ENDPOINTS`/`appendLog` 导出，测试 require 之；cursor database 测试改为调用 `initializeDatabase()` 真 schema。
2. **security.test.js 清理重复块（L160-196）**，并把 DoS 用例改为真实 POST 超长密码断言 413。
3. 前端字符串包含测试逐步替换为 jsdom + 真实执行内联 script，或至少降级合并为一个“冒烟结构”describe，把省出的预算投给 SSE 流翻译和认证链路。
4. engine-monitoring 的 Date.now 替换包 try/finally 或引入 fake timers。
5. e2e 用例去除固定 sleep，改 `expect(locator).toBeVisible()` 轮询；XSS 用例真正注入恶意 provider 名后断言渲染为文本。

## 八、任务总结

- **做了什么**：通读 4 个子模块共 21 个测试文件（~5,460 行）及对应生产代码，逐维度核对断言、mock、边界与缺口。
- **核心发现**：最大风险是“复制实现式伪测试”（codex-proxy 全部单元/集成测试、manager 的 crash-recovery/providers/security-DoS、cursor 的 database 层）；其次为前端字符串包含测试虚胖；hermes-proxy 与 cursor engine-monitoring 是正面样板。确认 8 处具体 bug/结构缺陷（含端口 fallback 死代码、测试文件合并残留、全局 Date.now 泄漏）。
- **未修改任何文件**；本报告即交付物。
- **遇到的问题**：部分测试中的 apiKey 字面量被读取工具脱敏显示为掩码，无法核实是否为真实密钥硬编码，建议人工复查 codex-proxy/tests 内嵌的 UPSTREAM_MODELS 配置来源。
