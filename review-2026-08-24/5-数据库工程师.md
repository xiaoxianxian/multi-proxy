# proxy-rebuild 数据库层字段级评审报告

## 一、Schema 设计

**做得好**
- `cursor-multi-model-proxy/src/db/database.ts:29-73`：五张表职责清晰；`models.provider_id` 带 `FOREIGN KEY ... ON DELETE CASCADE` 和 `UNIQUE(provider_id, id)`（database.ts:47-48），引用完整性好。
- `database.ts:107`：D1 迁移用 `CREATE UNIQUE INDEX unique_provider_id` 补齐 providers.provider_id 唯一性，思路正确（SQLite 不能 ALTER ADD CONSTRAINT）。

**问题**
1. **logs 表零索引**：`src/server/routes/adminRoutes.ts:153` 按 `ORDER BY timestamp DESC LIMIT ?` 查询、`database.ts:117` 按时间范围删除，都是全表扫描。建议 `CREATE INDEX idx_logs_timestamp ON logs(timestamp)`。
2. **models.name 无索引**：`src/server/handlers/chatHandler.ts:57-61` 每次聊天请求执行 `WHERE m.name = ? AND m.enabled = 1`，热路径全表扫描。
3. **主键由客户端提供**：`adminRoutes.ts:24,29` POST /providers 允许调用方传 `id` 作为 PK；`adminRoutes.ts:140-146` POST /routes 的 id 无格式校验、重复插入未捕获异常 → 500。对比之下 models 的 id 有正则校验（adminRoutes.ts:111），标准不一。
4. **routes.rules / fallback_chain 为裸 JSON TEXT**：无 CHECK(json_valid(...))，`max_retries` 无 `CHECK(max_retries >= 0)`，脏数据可直接入库（database.ts:51-58）。
5. **时间戳秒级精度且排序不稳**：全部 `datetime('now')`（TEXT，UTC 秒级）；`adminRoutes.ts:153` 仅按 timestamp 排序，同秒记录顺序不定。updated_at 无触发器，绕过 PUT 的直接 UPDATE 不会刷新。

## 二、事务使用与并发安全

**做得好**
- WAL 已开启、外键已开启（database.ts:14,17），且启动时 `wal_checkpoint(TRUNCATE)` 清理残留 WAL（database.ts:19-25）——这是很多项目漏掉的好细节。

**问题**
1. **全项目零事务**：`db.transaction` 在 src/ 下无任何出现。provider 删除→模型级联虽由 FK 保证，但「读 providers + 读 models」这类一致性读取（adminRoutes.ts:165-166）、settings 读改写都没有事务边界。
2. **每条 chat 请求写两次库**：`chatHandler.ts:25-26` 每个请求 `INSERT OR REPLACE` 持久化 rr_index，再插一条 log（chatHandler.ts:175）——round-robin 场景下每个请求 2 次磁盘 fsync，纯计数器放内存即可（重启偏差无关紧要）。
3. **未设 `busy_timeout`**：WAL 下写锁冲突默认立刻返回 SQLITE_BUSY。当前单进程独占 DB 问题不大，但没有防御性设置。
4. **错误处理不一致**：DELETE /providers 对 changes=0 返回 404（adminRoutes.ts:88-91），DELETE /models 却无条件返回 success（adminRoutes.ts:127-128）；POST /models、POST /routes 的 insert 异常未捕获，FK 冲突会变成裸 500。

## 三、加密存储实现

**做得好**
- AES-256-GCM，每次加密随机 12 字节 IV，tag 正确拼入密文（`src/utils/crypto.ts:70-77`）；key 文件 0o600（crypto.ts:43）；PBKDF2-SHA256 10 万轮派生（crypto.ts:55）。

**Bug / 风险**
1. **🔴 严重 Bug：key 文件路径基于 `process.cwd()`**（crypto.ts:29）。从不同工作目录启动服务会各自生成新密钥，导致已入库的所有 api_key 无法解密（decrypt 抛异常 → `findProviderConfig` 崩溃，chatHandler.ts:49/75/92 调用处无兜底）。应固定为 `path.join(__dirname, '../../data/')` 或 `os.homedir()`。
2. **PBKDF2 salt 硬编码固定值**（crypto.ts:54）：所有部署共用同一 salt，属 KDF 误用；且密文中未存储 kdf 参数/key 版本号，未来换参数即断代，无法平滑重加密。
3. **掩码逻辑失效**：`adminRoutes.ts:15-18` 截取的 `p.api_key.slice(0,4)` 是**密文**（IV 的前 2 字节 hex）而非明文前缀——既无展示意义也说明加密后未重新审视下游消费方。
4. **decrypt 无降级路径**：key 丢失/更换后没有「标记该 provider 密钥不可用、提示重新录入」的机制，直接 500。
5. 小优化：hex 编码使密文膨胀 2 倍，换 base64 可省 25% 存储。

## 四、JSON 文件 vs SQLite 选型

**结论：选型本身勉强合理（配置类小数据），但实现质量拖了后腿，且三套存储割裂。**

1. **🔴 codex/hermes 共享 `~/.multi-proxy-manager/providers.json` 却无并发保护**：两个独立进程整文件读-改-写，last-writer-wins 会静默丢更新；且**写盘非原子**——`codex-proxy/proxy.js:204` 和 `hermes-proxy/proxy.py:75-76` 都是直接 `writeFileSync/open('w')`，崩溃瞬间会产生截断的非法 JSON。讽刺的是同一个项目里 routing-mode.json 却正确用了 tmp+rename 原子写（proxy.js:143-145、proxy.py:104-106）——标准在同一 codebase 内不一致。
2. **🔴 明文 API key**：providers.json 里 api_key 明文落盘且文件权限为默认 0644（两处 save 均未设 mode），与 cursor 代理的 GCM 加密形成安全水位断层。至少应 `chmod 0o600`。
3. **架构割裂**：manager 统一管理三个代理，但供应商数据分散在 SQLite（cursor，含加密）和 JSON×2（codex/hermes，明文），三套 CRUD、三套校验逻辑（对比 P1-1 只统一了 id 格式）。长期看应收敛到单一存储。

## 五、迁移策略

1. **无版本化迁移机制**：未使用 SQLite 自带的 `PRAGMA user_version`，"迁移"是一串启动时内联 IIFE + try/catch（database.ts:80-138）。可运行但不可审计、不可回滚、无执行记录。
2. **D1 迁移半途而废**：`database.ts:100-103` 发现重复 provider_id 时仅 warn 并永久跳过——之后**每次启动**重复检查重复 warn，唯一约束永远加不上，脏数据持续存活。应在去重后再建索引（如保留 created_at 最新一条）。
3. **测试 Schema 手工复刻**：`tests/unit/database.test.ts:24-72` 把建表 SQL 原样复制进测试——生产 schema 一改测试即漂移失真；且 22 个测试全部打**裸 SQL**，生产路径（PUT 白名单动态 SQL、encrypt/decrypt 流程、路由 handler）完全未被测试覆盖。应从 database.ts 导出初始化函数供测试复用，并给 SecretsManager 补单测（尤其 round-trip 和错钥失败场景）。

## 六、备份与数据完整性

1. **零备份机制**：全仓库 grep `backup|.bak` 无结果。proxy.db 含加密 API key，`.encryption-key` 一旦丢失全部密钥作废，但无任何 key 备份指引或导出功能。
2. **DB 文件位置尚可但依赖模块相对路径**（database.ts:9 `../../data/proxy.db`），gitignore 已排除 *.db/-wal/-shm（.gitignore 末尾），这点没问题。
3. Manager 侧仅有 crash-recovery 状态文件（server.js:296），LOG_FILE 采用全量 rewrite（server.js:214），均非数据完整性方案。
4. 附带发现：`adminRoutes.ts:152` limit 无上限（`parseInt||100`），limit=10⁸ 可一次拉全表，建议 clamp 到 1000。

## 总评

| 维度 | 评价 |
|---|---|
| Schema | ★★★☆☆ 结构合理，缺索引、缺 CHECK、PK 校验不严 |
| 事务/并发 | ★★★★☆ better-sqlite3 同步单线程天然规避大部分问题；WAL+FK+checkpoint 到位 |
| 加密 | ★★★☆☆ 算法正确，但 cwd 密钥路径是必修 P0 |
| JSON 选型 | ★★☆☆☆ 非原子写 + 多进程共享 + 明文 key，三连击 |
| 迁移 | ★★☆☆☆ 无版本化，D1 静默放弃 |
| 备份 | ★☆☆☆☆ 完全缺失 |

**优先修复建议**：① crypto.ts:29 密钥路径改为固定位置（P0，现网已有数据面临不可解密风险）；② providers.json 写入补 tmp+rename + chmod 600（P0）；③ logs.timestamp / models.name 建索引；④ 引入 `PRAGMA user_version` 最小迁移框架；⑤ 制定 `.encryption-key` 备份策略。
